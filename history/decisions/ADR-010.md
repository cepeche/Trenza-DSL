# ADR-010: Three explicit context types (base, concurrent, overlay)

**Status**: Accepted  
**Date**: 2026-03-18  
**Source**: `history/chronicle/2026-03-18/03-resolucion-gaps-fase1.md`  
**Related GAPs**: Cuestión previa a GAP resolution  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Gemini 3.1 Pro, Lead Developer

---

## Context

In the early design phase (March 4–12, 2026), Trenza contexts were loosely typed: the language had no way to explicitly declare whether a context was a base state, a concurrent overlay, or something else. The type was inferred from usage patterns in the `transitions:` section, which is fragile.

For example:
- A **base context** is entered only from the initial state or from other base contexts.
- A **concurrent context** runs alongside other contexts without replacing them (e.g., a timer running in the background while a modal is open).
- An **overlay context** is always stacked on top of a base context (e.g., a dialog or modal).

The compiler needed explicit declarations of these intent for three reasons:

1. **Verification precision**: The verification rules differ for each type. For instance, a base context transition must be deterministic and reachable; a concurrent context can exit without notice.

2. **Code generation**: Different context types generate different Rust code. A base context generates a state enum; a concurrent context generates a managed task; an overlay generates a stack-managed struct.

3. **Opacity guarantees**: Early discussions (March 13, 2026) raised a concern about cryptographic opacity of system inputs. For the compiler to reason about what data flows where, it must know the context topology statically. Inferring topology from transitions is cumbersome.

---

## Decision

Three explicit context **kind** declarations exist. Each context must declare exactly one:

### Base contexts

Declare with `context NAME:` (no keyword modifier).

```trenza
context ModoNormal:
    input:
        actividades: Listado[Actividad]
    
    role display_actividades: Display (bind: actividades)
    
    transitions:
        on agregar_actividad -> ModoEdicion
```

**Semantics**:
- A base context is the "default" or "primary" context of the system. At any moment, exactly one base context is active.
- Only one base context can be active at a time.
- Transitions between base contexts replace the active context.

### Concurrent contexts

Declare with `context concurrent NAME:`.

```trenza
context concurrent SesionActiva:
    input:
        tarea_seleccionada: Tarea
    
    role display_timer: Display (bind: cronometro.tiempo_transcurrido)
    
    effects:
        [on_entry] -> cronometro.start(tarea_seleccionada.tareaId)
        [on_exit]  -> cronometro.stop()
```

**Semantics**:
- A concurrent context runs **alongside** one or more other contexts.
- Multiple concurrent contexts can be active simultaneously.
- A concurrent context can transition to deactivate itself without affecting other active contexts.
- Via `fills` (ADR-007), a concurrent context can add roles to overlays.

### Overlay contexts

Declare with `context overlay NAME:`.

```trenza
context overlay ModalComentario:
    input:
        mutable comentario: Comentario
    
    role campo_comentario: CampoTexto (bind: comentario.texto)
    
    transitions:
        on guardar.ok -> [close_overlay]
```

**Semantics**:
- An overlay is a context stacked **on top** of a base or concurrent context.
- Multiple overlays can be stacked.
- An overlay transitions away by closing itself (`[close_overlay]`) rather than transitioning to another context.
- Overlays are typically UI modals, popovers, or transient dialogs.

---

## Consequences

### Positive

- **Explicit intent**: The keyword (`context`, `context concurrent`, `context overlay`) makes the developer's intent clear and machine-verifiable.
- **Precise verification**: Verification rules can be specialized per context type. For example, "completeness" has different meaning for overlays (all handlers in the modal) vs. concurrent contexts (graceful degradation if concurrent context exits).
- **Readable code generation**: The Rust code generated for each type is structurally clearer and more efficient.
- **Tool support**: IDEs can warn if a transition chain violates the context hierarchy (e.g., trying to transition from a base context directly to an overlay).

### Negative / constraints

- **Context type cannot change**: Once a context is declared `overlay`, it cannot be used as a base. This is by design, but it can be surprising if a developer later wants to repurpose a context.
- **Strictness in topology**: The compiler rejects ambiguous transitions. Some valid use cases might require restructuring (e.g., if an overlay occasionally needs to transition to a different base, it must declare that in its declaration).

---

## Alternatives considered

1. **Infer context type from transition patterns**: Rejected. Inference is fragile; two independent developers might assume different inference rules for the same context.

2. **Single context type with annotations** (e.g., `#[concurrent]`): Rejected. Annotations feel optional. A keyword-based declaration makes the choice mandatory and visible.

3. **Subtype relationships** (e.g., `context overlay foo extends bar:` for inheritance): Rejected. For v0.0.1, explicit declaration without inheritance is clearer. Inheritance is a future decision (see ADR-013).

## Relation to other ADRs

- **ADR-001** (Trenza is a DSL): Explicit context types are part of making state machines transparent and verifiable.
- **ADR-003** (One file per context): Each context type is typically placed in its own file; naming conventions reflect the type.
- **ADR-007** (`slot` + `fills`): Overlay and concurrent contexts interact via `slot`/`fills`, which only works because their types are explicitly declared.
- **ADR-013** (Implicit inheritance): Context inheritance refers to this decision — overlays and concurrent contexts can inherit from base contexts.
- **Future ADR** (Context polymorphism): More advanced composition patterns may build on the foundation of explicit context types.
