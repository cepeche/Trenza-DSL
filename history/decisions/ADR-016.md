# ADR-016: Two types of guards: pre-action and post-result

**Status**: Accepted  
**Date**: 2026-03-18  
**Source**: `history/chronicle/2026-03-18/08-resolucion-gaps-fase2-opus.md` (GAP-3, GAP-5)  
**Related**: ADR-020 (Contract between actions and state machine)  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Gemini 3.1 Pro, Lead Developer

---

## Context

Conditional behavior in state machines typically arises in two distinct scenarios:

1. **Pre-action guards**: "Before we emit an event, check if it's valid to do so." Example: "don't save if the name field is empty."
2. **Post-result guards**: "After an action completes with a result, decide what happens next based on that result." Example: "if save succeeds, close the modal; if it fails with a recoverable error, retry."

Early designs conflated these two concerns or handled only one of them. However, they are fundamentally different:
- Pre-action guards are **synchronous, local, and preventive** — they avoid unnecessary work.
- Post-result guards are **asynchronous, reactive, and corrective** — they handle unexpected outcomes.

---

## Decision

Trenza supports **two distinct guard mechanisms**, each in its appropriate context.

### Type 1: Pre-action guards (in role handlers)

A `when` guard evaluates **before** emitting an event, based on the context's `input:` and role state:

```trenza
role boton_guardar: Boton
    on tap -> guardar(actividad) when actividad.nombre != ""
    on tap -> ignored when actividad.nombre == ""
```

**Semantics**:
- The guard is evaluated synchronously when the event occurs.
- If the guard is **true**, the action is emitted normally.
- If the guard is **false**, the handler action is skipped (and replaced by the alternative, typically `ignored`).
- The guard has access to `input:` fields and the role's own state, but not to external results.

**Purpose**: Prevent invalid or unnecessary actions from being dispatched to the external system.

### Type 2: Post-result guards (in transitions)

A `when` guard evaluates **after** an external action completes, based on the result payload:

```trenza
external api:
    action guardar(actividad: Actividad):
        ok -> Actividad
        error -> ErrorExterno

transitions:
    on guardar.error -> [close_overlay] when err.recuperable == false
    on guardar.error -> [stay] when err.recuperable == true
```

**Semantics**:
- The guard is evaluated after the action result (`.ok` or `.error`) is received.
- The guard has access to the result payload (e.g., `err: ErrorExterno`).
- If multiple transitions match the same event, the **first matching guard** determines the outcome.
- All transitions must be deterministic: no two can match the same event with the same result.

**Purpose**: Handle runtime variability (e.g., different types of errors) without introducing implicit conditional logic.

---

## Key differences

| Aspect | Pre-action (`when` in handler) | Post-result (`when` in transition) |
|--------|---------|----------|
| **Evaluated** | Before event emission | After result reception |
| **Scope** | `input:`, role state | Result payload |
| **Timing** | Synchronous, local | Asynchronous, reactive |
| **Purpose** | Avoid unnecessary work | Handle variability |
| **False branch** | Typically `ignored` | Another transition matches |

---

## Consequences

### Positive

- **Clarity**: Two guard mechanisms for two distinct purposes. No overloading of semantics.
- **Efficiency**: Pre-action guards prevent unnecessary external calls. Post-result guards handle only what actually occurs.
- **Verification clarity**: The compiler can check that pre-action guards evaluate only known, local data. Post-result guards are checked for exhaustiveness.
- **Error handling**: The two-guard model naturally accommodates both local validation and remote error handling.

### Negative / constraints

- **Learning curve**: New users must understand both guard types and their scopes.
- **Subtle bugs**: Confusing pre-action and post-result guards can lead to logic errors. Documentation must be clear.
- **Transition exhaustiveness**: When post-result guards are used, all possible results + guard combinations must be covered, or the verifier rejects the specification.

---

## Alternatives considered

1. **Single guard mechanism (pre-action only)**: Rejected. Post-result decisions (based on error types) cannot be expressed.

2. **Single guard mechanism (post-result only)**: Rejected. Local validation (pre-action) would require dispatching invalid requests to externals, wasting resources and exposing security issues.

3. **Implicit guards based on exception types**: Rejected. Exceptions are runtime failures; Trenza requires compile-time visibility.

4. **Allow guards in both directions, mixed**: Rejected. Mixing pre-action and post-result guards in the same transition confuses the evaluation order.

---

## Relation to other ADRs

- **ADR-020** (Contract between actions and state machine): Post-result guards are part of the contract — they react to `.ok` and `.error` branches.
- **ADR-014** (One action per handler): Pre-action guards do not change this rule; they control whether the action is emitted.
- **ADR-015** (ErrorExterno): Post-result guards access the `ErrorExterno` payload from failed actions.
- **ADR-001** (Trenza is a DSL): Both guard types make conditional logic explicit and verifiable.
