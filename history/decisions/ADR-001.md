# ADR-001: Trenza is a DSL, not a framework

**Status**: Accepted  
**Date**: 2026-03-04 (original session); consolidated 2026-03-20  
**Source**: `history/chronicle/2026-03-04/01-concepto-inicial.md`  
**Participants**: Lead Developer, Claude Sonnet 4.6, Claude Opus 4.6, Gemini 3.1 Pro

---

## Context

The Trenza project originated from a concrete problem: a developer with decades of experience encountered difficulty diagnosing a state-management bug in a modern event-driven JavaScript application. The bug (a modal appearing in the wrong mode) was caused by a conditional check `if (modoEdicion)` scattered across four distinct locations in the codebase. When one location was missing the guard, the resulting behavior was silent and difficult to trace.

The core insight was that in traditional object-oriented approaches, this "forgotten check" would become a compilation error if the state `modoEdicion` were represented as a polymorphic object rather than a boolean flag. This observation led to a broader question: **could a DSL encode state machines explicitly enough that missing cases become compilation errors, not runtime bugs?**

The project began as an exploration of this question under the working name "Helix DSL," inspired by the metaphor of a double helix — where specification and implementation are two complementary strands, each verifying the other. Early prototyping showed that from a single declarative specification, it was possible to generate not just one artifact (implementation) but multiple artifacts in parallel:
- Generated implementation (Rust)
- Generated tests (algebraic, effect-based)
- State diagrams (visual verification)
- Audit trails (compliance documentation)

This multi-artifact generation is the defining characteristic that distinguishes Trenza from frameworks. A framework is a library of reusable components. Trenza is a language that *generates* all necessary artifacts from a unified specification.

---

## Decision

Trenza is a **domain-specific language (DSL)**, not a framework.

### What this means

A **framework** is a collection of reusable libraries and conventions that developers use to build applications. The developer controls the flow and composition; the framework provides tools.

A **DSL** is a language in which the developer expresses a complete specification. The compiler or runtime interprets this specification to generate the full range of artifacts needed: code, tests, documentation, and verification artifacts.

Trenza operates at the level of specification: the developer writes `.trz` source files that declare contexts, roles, events, transitions, and effects. The Trenza compiler reads this specification and generates:
1. Executable Rust code (role handlers, state machine, concurrency primitives)
2. Test code (effect-based tests with pluggable implementations)
3. Verification artifacts (compliance reports, audit trails)
4. Visual artifacts (Mermaid diagrams)

This is fundamentally different from a framework like React or Spring, where the developer writes the application code directly and the framework provides utilities.

---

## Consequences

### Positive

- **Specification is canonical.** The `.trz` file is the source of truth. Everything else is derived. This eliminates the risk of documentation drifting from implementation.
- **Verification can be exhaustive.** Because the compiler sees the entire specification, it can enforce rules that span the whole system. For example, it can verify that every event is handled in every context, that transitions are reachable, and that effects don't introduce deadlocks.
- **Multiple teams can collaborate on artifacts without re-writing.** A frontend team generates the TypeScript layer; a backend team generates the Rust layer. Both teams build from the same `.trz` specification, ensuring consistency without manual coordination.
- **LLMs can participate in specification, not just implementation.** An LLM can help refine the specification itself (the `.trz`), not just write code. The specification is more amenable to collaborative refinement than implementation code.

### Negative / constraints

- **The DSL must be expressive enough for the domain.** If Trenza cannot express a requirement naturally, users will either work around it (e.g., embedding business logic in externals) or abandon it. Early design must invest heavily in expressiveness research.
- **The learning curve is steeper than a framework.** Developers must learn the DSL syntax and semantics. A framework can often be learned by copying examples; a DSL requires understanding the design principles.
- **The tool chain must be mature.** A framework has slack for immaturity (users can work around bugs by extending the framework). A DSL compiler bug often means users cannot proceed at all. This makes reliability non-negotiable early on.

---

## Alternatives considered

1. **Embed specification in code** (e.g., annotations in Rust or TypeScript): Rejected. This conflates the specification layer with the implementation layer. Verification becomes harder (the compiler must parse both), and multi-target generation becomes fragile.

2. **Create a framework instead**: Rejected. A framework approach would require developers to write state-machine code explicitly, defeating the purpose of having a specification. The bits of hand-written code are where the bugs hide (as in the original `modoEdicion` problem).

3. **Use an existing DSL or formal language** (e.g., Alloy, TLA+): Rejected. Existing formal languages are powerful but unreadable to most software engineers. Trenza's design principle (readability as a formal requirement) cannot be achieved by adopting an existing notation.

## Relation to other ADRs

- **ADR-002** (Rust + WASM): The choice of Rust as the compilation target follows directly from this ADR's requirement for exhaustive verification and multi-target generation.
- **ADR-003** (One file per context): A consequence of treating the context as the unit of specification. Each context is independently verifiable and deployable.
- **ADR-005** (Keywords in English): Part of the broader design principle that readability is formal. A DSL intended for human-AI collaboration must prioritize readability.
- **ADR-010** (Three explicit context types): The formalization of context types emerges from this ADR's commitment to making state machines explicit.
