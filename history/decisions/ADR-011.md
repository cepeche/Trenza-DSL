# ADR-011: Python prototype for v0.0.1; Rust for v1.0+

**Status**: Accepted  
**Date**: 2026-03-12  
**Source**: `history/chronicle/2026-03-12/02-decisiones-pendientes-claude.md` + `03-decisiones-pendientes-opus.md`  
**Related**: ADR-002 (Rust + WASM target), ADR-012 (JSON manifest)  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Lead Developer

---

## Context

The Trenza compiler must be built in some language. Two candidates emerged:

1. **Rust** (ADR-002's target): Provides compile-time verification, zero-cost abstractions, and seamless WASM compilation. Philosophically aligned with Trenza.
2. **Python** (prototyping): Faster iteration, lower friction for grammar exploration, easier to modify the parser/verifier as the language evolves.

The v0.0.1 phase is fundamentally a discovery phase: the grammar and verification rules are being finalized. Code written during this phase will reveal design gaps. Implementing the compiler in Rust immediately would mean either:
- Rewriting Rust code frequently as the grammar changes (wasteful), or
- Deferring grammar changes to avoid rewriting (conservative, suboptimal design)

Python allows rapid iteration without penalty. Once the grammar stabilizes (v1.0 readiness), rewriting in Rust is worthwhile. The transition should be verifiable: both compilers should produce identical AST output on the same input.

---

## Decision

**v0.0.1** uses a **Python prototype** compiler.  
**v1.0+** will use a **Rust production** compiler.

### Python prototype scope (v0.0.1)

The Python compiler focuses on core functionality:

1. **Parser** — reads `.trz` files, produces AST
2. **Verifier** — applies the 8 verification rules
3. **Document generator** — produces Markdown narrative docs
4. **Diagram generator** — produces Mermaid diagrams for visualization

**Explicitly OUT of scope** for Python:
- Code generation (beyond documentation)
- Performance optimization
- WASM compilation
- Production deployment

### Rust production compiler (v1.0+)

The Rust compiler will be feature-complete:

1. All functionality from Python plus:
2. **Code generation** — Rust, TypeScript, Go (multiple targets)
3. **LSP server** — for IDE integration (VS Code, JetBrains)
4. **WASM build pipeline** — compiles to `.wasm` modules
5. **Performance** — optimized parsing and verification

---

## Consequences

### Positive

- **Faster discovery**: Grammar gaps and verification rules are explored quickly in Python without the friction of Rust recompilation.
- **Parallel work**: While core grammar stabilizes, others can prototype code generators in Python (learning the patterns for Rust later).
- **Verifiable transition**: The Python AST becomes the contract. Rust output is validated against Python output, ensuring correctness.
- **Research velocity**: The human and LLM collaborators can focus on language design, not implementation details.

### Negative / constraints

- **False sense of completion**: A working Python prototype can be mistaken for a finished product. Discipline is required to commit to the Rust rewrite.
- **Duplication of effort**: Python and Rust code share no source; both must be written and maintained during the transition period.
- **User expectations**: Early adopters who use the Python prototype must be prepared for breaking changes and eventual deprecation.
- **Two parallel versions**: During late v0.0.x, both Python and Rust compilers may exist, causing confusion about which is authoritative.

---

## Criteria for Rust transition

The rewrite to Rust begins when:

1. **Grammar is stable**: No breaking changes to the `.trz` syntax for 2+ months.
2. **Verification rules are final**: All 8 rules are implemented in Python, tested on the reference implementation (CronometroPSP), and validated against expected behavior.
3. **AST format is frozen**: The Python AST JSON schema is documented and will not change (except backward-compatible extensions).
4. **Parser is comprehensive**: The Python parser handles all features in the spec and passes 100+ test cases derived from real `.trz` files.

**Timeline estimate**: v1.0 Rust compiler likely in Q3 2026, after 3+ months of Python v0.x iterations.

---

## Transition strategy: AST as contract

During the Python phase, the compiler emits an intermediate AST in JSON:

```bash
trenza parse myfile.trz > myfile.ast.json
```

When rewriting in Rust, both versions are tested:

```bash
trenza-python parse myfile.trz > ast1.json
trenza-rust parse myfile.trz > ast2.json
diff ast1.json ast2.json  # Must be identical
```

This ensures the Rust version is a faithful reimplementation, not a reinterpretation.

---

## Alternatives considered

1. **Implement in Rust immediately**: Rejected. Grammar iteration is slow; design gaps would be expensive to address.

2. **Use a language-agnostic format** (e.g., LLVM IR): Rejected. LLVM is verbose; Rust is both human-readable and machine-verifiable, making it the better target once stable.

3. **Implement in Go or C++**: Rejected. Rust's ownership system provides verification that aligns with Trenza's philosophy. Go lacks static guarantees; C++ has safety issues.

4. **Maintain Python and Rust compilers indefinitely** (feature parity): Rejected. Dual maintenance is expensive. Python is a prototype, not a long-term product.

- **ADR-002** (Rust + WASM target): This ADR defers the Rust implementation to v1.0 but confirms it as the strategic target.
