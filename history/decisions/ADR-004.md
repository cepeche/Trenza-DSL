# ADR-004: Rename Helix → Trenza

**Status**: Accepted  
**Date**: 2026-03-12  
**Source**: `history/chronicle/2026-03-12/01-nombre-helix-vs-trenza.md`  
**Participants**: Gemini 2.5 Pro (research and analysis), Claude Sonnet 4.6, Claude Opus 4.6, Lead Developer

---

## Context

The project began under the working name "Helix," inspired by the double-helix metaphor: specification and implementation are complementary strands, each verifying the other. Early design documents (2026-03-04 to 2026-03-06) used this name and associated file extensions (`.helix`, `.helixpkg`).

On 2026-03-12, Gemini 2.5 Pro conducted a trademark and ecosystem collision analysis. The findings revealed significant problems:

1. **Multiple existing projects share the name "Helix"**:
   - Helix (helix-lang.com): A systems programming language combining C++ performance with Rust safety
   - Helix DSL: An embedded DSL in Scala for machine-learning workflows
   - Helix: A formally verified rewriting engine in Coq (conceptually very close to Trenza)
   - Helix: A popular modal text editor written in Rust
   - Line 6 Helix: Hardware audio pedals using `.hlx` file extension

2. **Search visibility impact**: Using "Helix" guarantees low SEO ranking. The name collides with established projects, making it virtually undiscoverable.

3. **Risk of confusion**: The Helix formal-verification project is conceptually similar to Trenza (both generate code from specifications). The name collision creates real confusion risk.

Simultaneously, the design principle of Trenza had evolved. The initial "double helix" metaphor was being outgrown: a single specification generates not two artifacts but **three** (implementation, tests, audit trails), and conceptually **four** if we count the human-AI dialogue that drives refinement. A **trenza** (Spanish for "braid" or "three-strand plait") was a more accurate metaphor.

---

## Decision

The project is renamed from **Helix** to **Trenza**.

### Artifact name changes

| Artifact | Old | New |
|----------|-----|-----|
| DSL name | Helix | Trenza |
| Source file extension | `.helix` | `.trz` |
| Package extension | `.helixpkg` | `.tzp` |
| CLI command | `helix` | `trenza` |

### Rationale for the new name

**Trenza** (Spanish for "braid" or "plait"):

1. **Semantic evolution**: A double helix has two strands. A trenza has three — corresponding to the three core artifacts generated from a specification: implementation, tests, and verification documents. This is a more accurate metaphor than a double helix.

2. **Dimensionality upgrade**: The design principle of the human-AI dialogue adds a fourth dimension (the requirements emerging from conversation). Human interaction "weaves" the braided output.

3. **Identifiability**: Zero collisions with existing projects. The name is distinctive and easy to search.

4. **Internationalism**: Trenza is a Spanish word, reflecting the project's origins in a Spanish-speaking environment. It is memorable without being culturally specific.

---

## Consequences

### Positive

- **Clear identity**: Trenza is immediately distinguishable from other language projects.
- **Better SEO**: Developers searching for "Trenza DSL" or "trenza state machines" will find the project.
- **Accurate metaphor**: The name reflects the evolved design principle: three (or four) interwoven strands rather than two.
- **Trademark clarity**: The name can be registered without conflicts.

### Negative / transition costs

- **Documentation updates**: All docs, examples, and tutorials using "Helix" must be updated. This is primarily a one-time effort; automation can help (find-replace across repos).
- **Breaking change for early adopters**: If users had started projects with `.helix` files, they must rename files and update imports. CronometroPSP was renamed during its development, confirming this is manageable.
- **Changelog notation**: Future version histories must note this rename to avoid confusion when readers encounter old documents.

---

## Alternatives considered

1. **Keep "Helix" and disambiguate in marketing** (e.g., "Helix State Machine DSL"): Rejected. Disambiguation marketing is expensive and fragile. Search engines and human readers will still confuse the project with others.

2. **Choose another physics metaphor** (e.g., Quark, Lattice, Tensor): Rejected. Other physics metaphors either collide with existing projects or lack the elegance of "trenza."

3. **Use an acronym** (e.g., RDSM — "Role-Based DSL for State Machines"): Rejected. Acronyms are hard to remember and don't carry semantic weight.

4. **Rename only the file extensions** (keep "Helix" as the DSL name): Rejected. Partial renaming creates confusion (users see both names in documentation). A clean, complete rename is better.
