# ADR-015: `ErrorExterno` type and `.ok` / `.error` result branches

**Status**: Accepted  
**Date**: 2026-03-18  
**Source**: `history/chronicle/2026-03-18/08-resolucion-gaps-fase2-opus.md` (GAP-8)  
**Related**: ADR-020 (Contract between actions and state machine)  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Gemini 3.1 Pro, Lead Developer

---

## Context

In the design of external actions (API calls, side effects), the question arose: **how should errors be modeled?**

Early designs left error handling implicit: actions either succeeded or failed silently. This approach has several problems:

1. **No compile-time visibility**: The verifier cannot check that all failure paths are handled.
2. **Incomplete specifications**: A context might forget to handle the error case, resulting in undefined behavior.
3. **Loss of error context**: When an error occurs, there is no structured way to pass information (error code, message, severity) back to the state machine.

The solution is to make result branches explicit and typed. Every external action declares its possible outcomes at compile time, and the state machine must handle all of them.

---

## Decision

### 1. External actions declare result branches explicitly

Every action in an `external:` module declares its success and failure outcomes:

```trenza
external cronometro_api:
    action guardar(actividad: Actividad):
        ok -> Actividad          -- success branch: returns updated Actividad
        error -> ErrorExterno    -- error branch: returns error details
```

The `.ok` and `.error` branches are **mandatory** and **exhaustive**. No action can have only `.ok` without `.error` (unless truly infallible, which is rare).

### 2. `ErrorExterno` is a structured type

All errors conform to a single, extensible type defined in `data.trz`:

```trenza
data ErrorExterno:
    codigo: Texto          -- machine-readable code (e.g., "NETWORK_TIMEOUT")
    mensaje: Texto         -- human-readable message
    recuperable: Booleano  -- can the operation be retried?
```

**Why a single type?** 
- Unifies error handling across the entire system.
- Simplifies verification (the verifier only needs to know about `ErrorExterno`).
- Allows generic error-handling patterns (e.g., "if recuperable, retry; else abort").

### 3. Contexts must handle both branches

The verifier enforces that every context calling an external action handles **all declared branches**:

```trenza
transitions:
    on guardar.ok    -> [close_overlay]        -- success path
    on guardar.error -> [stay]                 -- error path (mandatory)
```

Omitting either branch is a **Completeness violation** (Rule 1). The compiler rejects the specification.

### 4. Error context flows through `effects:`

When an error occurs, the error object can be passed to `effects:` for logging, state updates, or user notification:

```trenza
transitions:
    on guardar.error -> [stay]

effects:
    [on guardar.error(err)] -> ultimo_error.asignar(err.mensaje)
    [on guardar.error(err)] -> auditLog.registrar("guardar falló", err.codigo)
```

The error payload `err` is available in the effect context, allowing structured error handling.

---

## Consequences

### Positive

- **Exhaustive verification**: The compiler proves that every error outcome is handled.
- **No silent failures**: An error is an observable event, not a lost exception.
- **Structured error information**: Error codes and messages enable programmatic handling (retries, user messaging, logging).
- **Audit trail**: All errors are logged through `effects:`, supporting compliance requirements.
- **Refactoring safety**: If a new error branch is added to an action, the compiler reports all contexts that must be updated.

### Negative / constraints

- **Verbosity**: Every external call requires explicit error handling. No implicit error propagation.
- **No exception hierarchy**: Unlike OOP exceptions, there are no specialized error types. All errors use the same `ErrorExterno` structure.
- **Runtime overhead**: The `.ok` / `.error` branching adds some runtime dispatch. However, this is negligible compared to the actual external operation.

---

## Alternatives considered

1. **Implicit success/failure** (try-catch style): Rejected. No compile-time visibility.

2. **Multiple error types** (e.g., `NetworkError`, `ValidationError`, `AuthError`): Rejected. Complicates verification; each error type requires its own transition rules.

3. **Optional return values** (e.g., `guardar -> Actividad?`): Rejected. Losing the error context means the state machine cannot make decisions based on *why* an action failed.

4. **Exceptions that unwind the stack**: Rejected. Trenza does not support exception semantics; all state transitions are explicit.

---

## Relation to other ADRs

- **ADR-020** (Contract between actions and state machine): This ADR specifies the `.ok` / `.error` protocol that ADR-020 formalizes.
- **ADR-014** (One action per handler): External actions, like role handlers, emit exactly one "action" (which triggers `.ok` or `.error`).
- **ADR-006** (`effects:` instead of `lifecycle:`): Error effects are declared in the `effects:` section, making error handling explicit and auditable.
- **Future ADR** (Error recovery strategies): Policies for automatic retry, fallback contexts, or error escalation may be formalized later.
