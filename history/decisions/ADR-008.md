# ADR-008: `forbidden` keyword for explicitly prohibited events

**Status**: Accepted  
**Date**: 2026-03-20 (confirmed); earlier decision in 2026-03-04 (as `bloqueado`)  
**Source**: `history/chronicle/2026-03-04/02-diseno.md`, `history/chronicle/2026-03-20/03-resolucion-gap4-definitiva.md`  
**Related**: ADR-005 (Keywords in English), ADR-014 (One action per handler)  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Gemini 2.5 Pro, Lead Developer

---

## Context

In the original design (March 4, 2026), Trenza had three ways to respond to an event:

1. **Handle the event** with an action: `on tap -> mostrarActividades`
2. **Ignore the event silently**: `on tap -> ignored` (later formalized in ADR-014)
3. **Explicitly forbid the event**: `on tap -> bloqueado`

The third option was important for security and compliance: when a certain event is **not allowed** in a context (e.g., editing is forbidden during a read-only session, or deletion is forbidden for certain users), Trenza should make this prohibition explicit and verifiable.

The keyword `bloqueado` (Spanish for "blocked") was used initially. However, when ADR-005 (Keywords in English) was ratified, consistency required changing `bloqueado` to its English equivalent: `forbidden`.

The distinction between `ignored` and `forbidden` is crucial:
- **`ignored`** — the event is not handled; it is silently discarded.
- **`forbidden`** — the event is explicitly not allowed; an attempt to emit it is a violation (observable and auditable).

---

## Decision

The keyword **`forbidden`** is reserved for explicitly prohibiting events in a context.

### Syntax

```trenza
role boton_borrar: Boton
    on tap -> forbidden    -- deletion is not permitted in read-only mode
```

### Semantics

When a handler declares `on event -> forbidden`:

1. **Verification**: The compiler records this as an explicit prohibition.
2. **Runtime behavior**: Attempting to emit this event triggers a `[on_violation]` observable event (see ADR-014), allowing audit logging and policy enforcement.
3. **Audit trail**: The `forbidden` declaration is captured in the audit report, making compliance constraints visible.

### Comparison with `ignored`

| Aspect | `ignored` | `forbidden` |
|--------|-----------|------------|
| **Intent** | Not applicable | Not permitted |
| **Event dispatch** | Silently discarded | Emits `[on_violation]` |
| **Audit trail** | No record | Logged as policy violation |
| **Use case** | Unused features in a mode | Security/compliance constraints |

---

## Consequences

### Positive

- **Compliance by design**: Security policies (e.g., "users cannot delete in read-only mode") are expressed as language constructs, not hidden in implementation.
- **Observable violations**: A `forbidden` event triggers a violation event that can be logged, metered, or used to enforce policies.
- **Clear intent**: Developers reading a `.trz` file immediately understand that a certain action is structurally prohibited, not just unimplemented.
- **Verification opportunity**: The compiler can reason about which operations are forbidden in which contexts, supporting compliance audits.

### Negative / constraints

- **Runtime overhead**: Unlike `ignored` (which has no runtime cost), `forbidden` may require runtime checks and violation event dispatch.
- **Event explosion**: In a system with many forbidden operations, the violation event stream could become noisy. Tools must allow filtering violations by severity or policy.

---

## Alternatives considered

1. **Omit forbidden entirely; let unhandled events silently fail**: Rejected. This defeats the purpose of making security constraints explicit.

2. **Use exceptions instead of a language keyword**: Rejected. Exceptions are runtime failures; Trenza requires compile-time visibility of forbidden operations for verification.

3. **Allow `forbidden` to accept a reason/message**: `on tap -> forbidden("deletion not permitted")`. Rejected for v0.0.1. The reason belongs in documentation and the `@audit` annotation (ADR-019), not in the language syntax.

4. **Use a different keyword** (e.g., `blocked`, `denied`, `prohibited`): Rejected. `forbidden` is more concise and aligns with English security terminology.

---

## Relation to other ADRs

- **ADR-005** (Keywords in English): `forbidden` is an English keyword, consistent with all others in Trenza.
- **ADR-014** (One action per handler): Both `ignored` and `forbidden` satisfy the constraint that a handler emits exactly one "action" (in this case, a no-op or a violation event).
- **ADR-019** (`@intent` annotation): Forbidden operations are often paired with `@audit("reason")` for compliance documentation.
- **ADR-020** (Contract between actions and state machine): A `forbidden` event is an observable event, emitted through the violation channel.
- **Future ADR** (Violation handling): Policies for responding to forbidden events (log, alert, escalate) may be defined in a dedicated ADR.
