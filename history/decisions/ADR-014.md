# ADR-014: One action per handler

**Status**: Accepted
**Date**: 2026-03-18 (original memo); consolidated as ADR during v0.0.1 triage (2026-03-20)
**Source**: `history/chronicle/2026-03-18/06-memo-opus-resolucion-gap2.md`
**Previous decisions consulted**: memo GAP-1/GAP-7 (separation of `input:` / `bind:` / `effects:` layers), memo GAP-2 original (Claude's two syntactic alternatives).
**Participants**: Lead Developer, Claude Opus 4.6, Claude Sonnet 4.6, Gemini 3.1 Pro.

---

## Context

GAP-2 of the March 2026 gap review asked how to express "multiple effects in a
single event". Two syntactic alternatives had been proposed:

```trenza
-- Option A: inline list
on guardar -> [actualizarNombre(campo.valor), cerrarOverlay]

-- Option B: do-block
on guardar -> do:
    actualizarNombre(campo.valor)
    cerrarOverlay
```

The question was implicitly which of the two to adopt. The actual resolution
showed the question to be malformed: once the three-layer model from GAP-1/GAP-7
was in place (`input:` / `bind:` / `effects:`), most apparent "compound actions"
turned out to be *one domain action plus a state change*, which the language
already expresses cleanly across three distinct sections.

| What it looked like | What it actually is |
|---------------------|---------------------|
| `guardar + cerrarOverlay` | action (`guardar`) + transition (`-> [close_overlay]`) |
| `descartar + cerrarOverlay` | action (`descartar`) + transition (`-> [close_overlay]`) |
| `cargarDatos + iniciarTimer` | two domain effects in `[on_entry]` |

A role handler emits one event. The transition provoked by that event is
declared in `transitions:`. Domain effects live in `effects:`.

---

## Decision

Handlers in roles and rules in `transitions:` accept **exactly one action or
event per line**. The `effects:` section accepts multiple lines per lifecycle
trigger by repeating the trigger.

### Role handlers: exactly one action

```trenza
role boton_guardar: Boton
    on tap -> guardar(actividad_en_edicion)

transitions:
    on guardar -> [close_overlay]
```

The handler emits `guardar`. The transition answers by closing the overlay.
These are two separate responsibilities, not one compound action.

### `effects:`: one action per line, triggers repeat

If a lifecycle trigger needs to fire more than one domain effect, the
trigger is repeated:

```trenza
effects:
    [on_entry] -> cronometro.start(tarea.id)
    [on_entry] -> analytics.track("session_start")
    [on_exit]  -> cronometro.stop()
```

Semantics: all `[on_entry]` lines execute on entry, in the order declared.
The verifier reasons about each line independently.

### Formal rule

| Section | Rule |
|---------|------|
| Role handler (`on event ->`) | Exactly one action or event |
| `transitions:` | Exactly one transition per event |
| `effects:` | One action per line; trigger repeats if several are needed |

---

## Consequences

### Positive

- **The grammar does not grow.** GAP-2 is resolved without adding inline list
  syntax `[a, b, c]` nor `do:` blocks. The grammar stays minimal.
- **Separation of concerns is pushed into the author.** "Save and notify and
  close" is a signal that responsibilities were not cleanly separated at the
  design stage. Trenza specifies *what* happens; *how* belongs to the
  implementation of the domain action (typically an `external` module).
- **Verification stays line-by-line.** Each line in `effects:` is an
  independent assertion. Coverage tools can report per-line, not per-composite.

### Negative / residual

- An author who needs "guardar AND notify AND close" in a single handler must
  express it as a domain operation in an `external` module that internally
  orchestrates the three calls. This may be seen as verbose for quick
  prototypes.
- The restriction is a design guard, not a syntactic impossibility. A future
  ADR could relax it if practice demonstrates genuine need. **Restrictions
  are easier to relax than to tighten**, so starting strict is the correct
  direction.

---

## Alternatives considered

1. **Option A — inline list** (`[a, b, c]`): rejected. Conflates "one event
   with several actions" with "one action that produces several effects". The
   conflation survives into generated code and into verification outputs.

2. **Option B — `do:` block**: rejected. Introduces a new grammar construct
   purely for cosmetic convenience over what three already-existing sections
   already express. The section-based resolution is equally readable.

3. **Allow both Option A and Option B depending on author preference**:
   rejected. Multiplies the ways the same meaning can be expressed, which
   breaks canonical hashing (ADR-021) and makes review harder.

---

## Relation to other ADRs

- **ADR-013** (`on_violation` as observable event): uses the same principle —
  a forbidden action is not a compound of "log + throw"; it is a single event
  dispatched through the violation channel.
- **ADR-019** (`@intent` annotation): decorators attach to a single handler;
  this ADR guarantees that "single handler" has unambiguous meaning.
- **ADR-021** (public surface and canonical form): canonical hashing is
  well-defined only if each line carries exactly one action. This ADR is a
  prerequisite for deterministic canonical form.

---

**Closing note**: this ADR is an example of a design question whose best
answer is "the question is framed wrongly, and the language we already have
answers it once the framing is corrected". No new syntax was needed — only
consistent use of the three sections the language already provides.
