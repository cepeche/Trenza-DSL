# ADR-006: `effects:` instead of `lifecycle:`

**Status**: Accepted  
**Date**: 2026-03-18  
**Source**: `history/chronicle/2026-03-18/05-memo-opus-resolucion-gap1-gap7.md`  
**Related GAPs**: GAP-1, GAP-7  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Gemini 3.1 Pro, Lead Developer

---

## Context

During the specification of lifecycle events in Trenza contexts, the project needed a keyword to denote side effects that occur when a context is activated or deactivated. Two candidate names emerged:

1. **`lifecycle:`** — inspired by React, Angular, and other frontend frameworks where lifecycle hooks handle setup and teardown.
2. **`effects:`** — inspired by algebraic effects in formal semantics, emphasizing that these are domain effects, not framework infrastructure.

The choice between them was not merely semantic. The term "lifecycle" carries implicit baggage from frontend frameworks, where lifecycle hooks are conflated with UI framework details (DOM manipulation, renderer coordination, garbage collection). In contrast, "effects" emphasizes that Trenza's model is about domain-level actions — starting a timer, logging an audit trail, acquiring a resource lock — not about framework machinery.

This distinction matters for tool design and documentation. If developers see `lifecycle:`, they may assume it is a hook for framework-specific concerns. The term `effects:` makes clear that these are **domain-level side effects**, verifiable and auditable in the same way as the rest of the specification.

---

## Decision

The keyword is **`effects:`**, not `lifecycle:`.

### Syntax

```trenza
context SesionActiva:
    input:
        tarea_seleccionada: Tarea
    
    effects:
        [on_entry] -> cronometro.start(tarea_seleccionada.tareaId)
        [on_exit]  -> cronometro.stop()
        [on_exit]  -> analytics.track("session_ended")
```

### Trigger keywords

Two lifecycle triggers are supported:
- **`[on_entry]`** — fires when the context becomes active
- **`[on_exit]`** — fires when the context becomes inactive (transitioning away or being suspended)

### Scope of effects

An `effects:` section is not a dumping ground for imperative code. It declares domain-level effects only:

| ✅ Valid | ❌ Invalid |
|---------|----------|
| `-> cronometro.start()` | `-> if (condition) { ... }` |
| `-> auditLog.register()` | `-> let x = 5; x += 3` |
| `-> cache.invalidate()` | `-> console.log()` (unless it's domain logging) |

An effect is a call to an external action or domain service. No local computation, no conditionals.

---

## Consequences

### Positive

- **Clarity of intent**: `effects:` immediately signals "these are domain-level side effects," not framework machinery.
- **Connection to formal semantics**: `effects:` aligns with the academic tradition of algebraic effects, making formal verification and reasoning more natural.
- **Separation of concerns**: Domain effects are visually distinct from state transitions and role bindings. Each section has a clear purpose.
- **Multi-artifact generation**: The `effects:` section maps cleanly to:
  - Rust: `Future`-based async action calls
  - TypeScript: Promise-based effect execution
  - Audit: Explicit effect logging for compliance

### Negative / constraints

- **Friction with frontend developer expectations**: Developers coming from React or Angular may expect `lifecycle:` hooks. Documentation must explain the difference clearly.
- **`effects:` is a term with multiple meanings**: In functional programming, "effect" can mean "side effect" or "algebraic effect" or even "visual effect." Trenza's documentation must define it precisely.

---

## Alternatives considered

1. **`lifecycle:`** — The framework-inspired name. Rejected because it invokes framework semantics that Trenza deliberately avoids.

2. **`handlers:`** — Could work, but is too general. Trenza already uses `role ... (on event ->)` handlers for role event handlers. Using `handlers:` for lifecycle would be confusing.

3. **`initialize:` + `finalize:`** — Two separate sections. Rejected because they are semantically parallel and should be visually grouped.

4. **`sideffects:` or `sideeffects:`** — Phonetically awkward and less formal.

## Relation to other ADRs

- **ADR-001** (Trenza is a DSL): The `effects:` section is part of making state machines explicit and verifiable.
- **ADR-007** (Reserved keyword `ignored`): Role handlers can emit `ignored`; effects are the domain-level consequences of state transitions.
- **ADR-020** (Contract between actions and state machine): `effects:` is one side of the contract — it declares what the state machine will do when transitioning.
- **Future ADR** (Test generation): The test generator will verify that all `[on_entry]` effects are called when a context is activated.
