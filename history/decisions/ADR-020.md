# ADR-020: The contract between actions and the state machine

**Status**: Accepted
**Date**: 2026-03-23
**Source**: Review of Gemini's examples (2026-03-22); analysis by Claude Opus 4.6 + Claude Sonnet 4.6
**Participants**: Lead Developer, Claude Opus 4.6, Claude Sonnet 4.6

---

## Context

When canonizing Gemini's examples (`examples/autenticacion-rgpd.trz` and
`examples/carrito-checkout.trz`), three design questions arose that the
v0.0.1 manual did not resolve explicitly:

1. How are arguments passed to an external module from the `effects:` section?
2. What syntax do result events from an external call use in `transitions:`?
3. Can an action emit a transition event with a name different from its own?

All three questions are manifestations of the same problem: **what is the contract
between an action and the state machine**. They are resolved in a unified manner.

---

## Decisions

### D1 — Arguments in `effects:`: `input:` names are referenced

In the `effects:` section, the arguments of external calls are names
declared in the context's `input:`. `self` is not valid outside of
role handlers.

```trenza
context Autenticando:
    input:
        credenciales: Credenciales

    effects:
        [on_entry] -> verificar_credenciales(credenciales)
```

This is consistent with the already-established rule that `when` guards can only
evaluate the context's `input:`. Effects follow the same visibility scope.

**Consequence**: when a role needs to pass its data to an external, it must
bind to a `mutable` field of `input:` via `bind:`. The external receives
that field, not `self` directly.

### D2 — External results: structural suffixes `.ok` / `.error`

The result branches of an external are declared explicitly in its
definition. Transitions and effects react to those branches via
the syntax `action.ok` / `action.error`.

```trenza
external auth_api [authorized_for: personal]:
    action verificar_credenciales(creds: Credenciales):
        ok -> TokenSesion
        error -> ErrorExterno

-- In the invoking context:
transitions:
    on verificar_credenciales.ok    -> SesionActiva
    on verificar_credenciales.error -> EsperandoCredenciales
```

The verifier requires that every context invoking an external action handles
**all** its declared branches, whether in `transitions:` or in `effects:`. Omitting
a branch is a compilation error (extension of Rule 1 — Completeness).

**Discarded**: free names such as `authExito`/`authFallo`. They break
traceability: the compiler cannot know that `authExito` corresponds to the
result of `verificar_credenciales` without an additional redundant declaration,
and cannot detect unhandled branches.

### D3 — Actions do not emit events: topology does that work

An action cannot emit an event with a name different from its own. The
mechanism of "the action decides which event to emit based on internal state"
does not exist.

The situation that motivates this question — "in `CarritoVacio`, the first item
activates the cart; in `CarritoActivo`, additional items do not change context" —
is modeled with context topology:

```trenza
context CarritoVacio:
    role item_catalogo: ProductoCatalogo
        on añadir -> agregar_item(self.id)

    transitions:
        on agregar_item.ok -> CarritoActivo    -- the first item transitions

context CarritoActivo:
    role item_catalogo: ProductoCatalogo
        on añadir -> agregar_item(self.id)    -- same action

    transitions:
        on agregar_item.ok -> [stay]           -- subsequent ones do not transition
```

The same action `agregar_item` produces different results depending on the active
context, without any conditional. The factory instantiates the context; the topology
does the work that an `if (carrito.isEmpty())` would do.

**Discarded**: derived events such as `agregarAlCarrito.primerItem`. Any
mechanism where the action "decides" which sub-event to emit introduces hidden
conditional logic inside the action, outside the scope of the verifier.

## Code generation examples

### How the contract materializes in Rust

Given this `.trz` specification:

```trenza
external auth_api:
    action verificar_credenciales(creds: Credenciales):
        ok -> TokenSesion
        error -> ErrorExterno

context Autenticando:
    input:
        credenciales: Credenciales
    
    effects:
        [on_entry] -> verificar_credenciales(credenciales)
    
    transitions:
        on verificar_credenciales.ok -> SesionActiva
        on verificar_credenciales.error -> [stay]
```

The compiler generates (Rust, Strand 1):

```rust
pub fn autenticando_on_entry(
    context: &mut AutenticandoContext,
    effects: &dyn Effects,
) {
    // Call the external action with input: data
    match effects.verificar_credenciales(&context.credenciales) {
        Ok(token) => {
            context.last_token = token;
            // Transition determined by .ok branch
            context.state = AutomataState::SesionActiva;
        }
        Err(err) => {
            context.last_error = err;
            // Transition determined by .error branch (.stay)
            // (no state change)
        }
    }
}

// Effects trait: allows mocking in tests
pub trait Effects {
    fn verificar_credenciales(
        &self,
        creds: &Credenciales,
    ) -> Result<TokenSesion, ErrorExterno>;
}
```

### How the contract materializes in TypeScript

Same specification, TypeScript target (future Strand 1 variant):

```typescript
export async function autenticando_on_entry(
    context: AutenticandoContext,
    effects: Effects,
): Promise<AutomataState> {
    try {
        const token = await effects.verificar_credenciales(
            context.credenciales,
        );
        context.lastToken = token;
        return AutomataState.SesionActiva;  // .ok transition
    } catch (err) {
        context.lastError = err as ErrorExterno;
        return AutomataState.Autenticando;  // .stay transition
    }
}

export interface Effects {
    verificar_credenciales(
        creds: Credenciales,
    ): Promise<TokenSesion>;
    // Errors are thrown and caught; no Err type needed
}
```

**Key observation**: The contract (`.ok` → transition 1, `.error` → transition 2) is compiled into the control flow of generated code. The verifier ensures all branches are handled **at compile time**; runtime cannot skip a branch.

---

## Unified pattern

The complete contract between actions and the state machine:

```
role handler → action(args via self or input) → typed result → transition by context
              does not decide which event       .ok / .error    topology + when
              statically verifiable             exhaustive       declarative
```

Four invariants:
- The **data scope** in handlers is `self`; in `effects:` it is `input:`.
- The **result branches** of an external are closed and declared in its definition.
- **Local actions** do not declare branches; they produce exactly one implicit result.
- **Conditional logic** over results lives in `when` guards or in topology,
  never inside actions.

---

## Consequences

- The files `examples/autenticacion-rgpd.trz` and `examples/carrito-checkout.trz`
  reflect this pattern and serve as canonical references.
- The manual (sections 3.4 and 4.4) is already aligned with D2. No changes required.
- Section 4.3 of the manual should explicitly clarify that `self` is not valid
  in `effects:` (a notable absence, not a contradiction).
- A new verification rule derived from D2: exhaustiveness of external branches.
