# ADR-005: Keywords in English

**Status**: Accepted  
**Date**: 2026-03-06 (principle established); 2026-03-20 (consolidated); 2026-03-23 (applied to `deactivate` keyword)  
**Source**: `history/chronicle/2026-03-06/` (decision memos); applied consistently in language grammar  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Gemini 3.1 Pro, Lead Developer

---

## Context

During the design phase (March 2026), the project team had to decide on the language of keywords in Trenza. Two options emerged:

1. **Spanish keywords**: Align with the project's Spanish-speaking origins and the use of Spanish in domain models (e.g., `ModoEdicion`, `ActividadActiva`). This choice felt natural to the team.

2. **English keywords**: Follow the global software engineering convention that programming languages use English keywords. This improves adoption in international teams and makes the language learnable for non-Spanish speakers.

The decision became clear when considering:

- **LLM collaboration**: Claude, Gemini, and other English-language LLMs have been trained primarily on English-language code. English keywords make LLM-generated examples and documentation more consistent with the training data.
- **Academic rigor**: The target audience for academic papers (ONWARD! 2026) is international. English keywords make the paper's code examples immediately readable.
- **Internationalism**: Spanish is spoken by ~500M people; English (as a technical lingua franca) is understood by billions of developers. Keywords in English expand reach without sacrificing the Spanish cultural context (which is preserved in domain names and documentation).
- **Precedent**: Python (with non-English contributors) uses English keywords. The same is true of Rust, Go, and virtually all modern languages. This is the established norm in programming language design.

The team agreed to use **English keywords** while allowing domain concepts (context names, role names, variable names) to be in any language.

---

## Decision

All **Trenza language keywords** are in English. Domain concepts (context names, role names, external module names, input/output field names) may be in any language, preferably matching the domain's natural language.

### Examples

**Keywords (English)**:
```trenza
context     external      role          on            input:
output:     effects:      transitions:  when          action
slot        fills         overlay       concurrent    base
[on_entry]  [on_exit]     .ok           .error        [deactivate]
[stay]      [close]       [ignore]      mutable       bind:
```

**Domain concepts (any language)**:
```trenza
context ModoEdicion:
    input:
        actividad_en_edicion: Actividad
    
    role boton_guardar: Boton
        on tap -> guardar(actividad_en_edicion)
```

Here, `context`, `input`, `role`, `on` are English keywords. But `ModoEdicion`, `actividad_en_edicion`, `boton_guardar`, and `Actividad` can be in Spanish (or any language).

---

## Consequences

### Positive

- **LLM collaboration**: English keywords align with LLM training data. Claude and Gemini generate more natural examples when keywords are English.
- **Academic communication**: Papers and documentation are immediately readable to international audiences. Code examples don't require translation.
- **Tool compatibility**: Syntax highlighters, IDE plugins, and linters can leverage existing conventions for English keywords.
- **Learner ergonomics**: Developers familiar with Python, Rust, or JavaScript can immediately recognize Trenza's keyword structure.
- **Mixed-language expressions**: A developer can write `context ModoEdicion:` using English `context` and Spanish `ModoEdicion`. This reads naturally in mixed-language environments.

### Negative / constraints

- **Spanish-speaking teams may feel alienated**: The project is rooted in Spanish-language development, but keywords are not Spanish. This is a minor cultural trade-off for global accessibility.
- **Inconsistency in documentation**: Domain names are Spanish (e.g., in CronometroPSP), but keywords are English. This requires discipline in documentation to make the distinction clear.

---

## Alternatives considered

1. **Spanish keywords throughout**: Rejected. This limits international adoption and misaligns with LLM training data.

2. **Bilingual keywords** (both English and Spanish versions, user's choice): Rejected. This multiplies verification rules and breaks canonical form (see ADR-021). Two ways to write the same meaning is a design anti-pattern.

3. **Machine-generated translations of keywords**: Rejected. Automatic translation of keywords would result in awkward phrasing (e.g., `sobre` for `on`, `entradas` for `on_entry`) that is less readable than English.

4. **Allow keywords in any language, derived from the local locale**: Rejected. This breaks reproducibility and makes code unreadable across locales.

---

## Relation to other ADRs

- **ADR-001** (Trenza is a DSL): Readability is a formal requirement of Trenza's design. English keywords maximize readability for a global audience.
- **ADR-004** (Helix → Trenza rename): The project name is Spanish, but keywords are English. This reflects the international nature of the final product while honoring the Spanish origins.
- **ADR-021** (Canonical form and public surface): Keywords must be in a fixed language to ensure canonical hashing is deterministic. English is the chosen canonical language.
- **Verb forms**: `[deactivate]` was preferred over `[desactivar]` for consistency, even though the domain uses Spanish. This applies across all keywords (e.g., `[on_entry]` not `[al_entrar]`).
