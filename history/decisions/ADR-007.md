# ADR-007: `slot` + `fills` mechanism for context composition

**Status**: Accepted  
**Date**: 2026-03-20  
**Source**: `history/chronicle/2026-03-20/03-resolucion-gap4-definitiva.md`  
**Related GAP**: GAP-4 (conditional roles in overlays)  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Gemini 2.5 Pro, Lead Developer

---

## Context

Trenza allows multiple contexts to be active simultaneously: a base context (e.g., `ModoEdicion`), a concurrent context (e.g., `SesionActiva`), and overlays (e.g., `ModalComentario`). The question arose: **how does a concurrent context add roles or effects to an overlay when both are active?**

For example, in CronometroPSP:
- `ModalComentario` (overlay) has a text input for comments
- `SesionActiva` (concurrent) is active when a task session is running
- When both are active, an additional checkbox should appear: "Sustituir sesión existente"

The naive solution would be to add a conditional in `ModalComentario`:

```trenza
role checkbox_sustituir: Checkbox  when SesionActiva.isActive
    on change -> marcarSustituir(self.marcado)
```

But this reintroduces implicit conditionals — exactly what Trenza is designed to eliminate. The problem was **GAP-4: how to make conditional roles explicit at the compositional level?**

The solution is a two-part mechanism: **`slot`** in overlays and **`fills`** in concurrent contexts. This is a Trenza-specific adaptation of DCI (Data-Context-Interaction), with explicit extension points instead of implicit role mixing.

---

## Decision

### Mechanism: `slot` for extension points

An overlay can declare **extension points** (named `slot`s) that are empty by default:

```trenza
context ModalComentario:
    input:
        mutable comentario: Comentario
    
    role campo_comentario: CampoTexto (bind: comentario.texto)
    role boton_guardar: Boton
        on tap -> guardar(comentario)
    
    slot sesion_opts    -- empty by default
    
    transitions:
        on guardar.ok -> [close_overlay]
```

### Mechanism: `fills` for providing roles

A concurrent context can fill a `slot` with additional roles and effects:

```trenza
context SesionActiva:
    input:
        tarea_seleccionada: Tarea
    
    role display_timer: Display (bind: cronometro.tiempo_transcurrido)
    
    effects:
        [on_entry] -> cronometro.start(tarea_seleccionada.tareaId)
    
    fills ModalComentario.sesion_opts:
        role checkbox_sustituir: Checkbox
            on change -> marcarSustituir(self.marcado)
        
        effects:
            [on_entry] -> sesiones_api.cargar_recientes()
```

### Semantics

- The `checkbox_sustituir` role **exists only when both `SesionActiva` and `ModalComentario` are simultaneously active**.
- If `SesionActiva` is inactive, the checkbox does not exist. This is not a boolean `display: none`; it is a structural absence.
- The effects in the `fills` block execute when the combined context (concurrent + overlay) becomes active.

---

## Consequences

### Positive

- **Explicit composition**: The fact that `SesionActiva` adds roles to `ModalComentario` is visible in both files. There is no hidden conditional.
- **Verification is precise**: The verifier can check that the slot exists, that all added roles are valid, and that transitions are deterministic within the combined context.
- **Avoids state explosion**: Instead of parameterizing overlays on concurrent status (which would multiply contexts), the `slot`/`fills` mechanism composes them declaratively.
- **Modular reasoning**: An overlay developer can see at a glance which slots are available and understand how other contexts will extend the overlay.

### Negative / constraints

- **Syntax is unfamiliar**: `slot` and `fills` are not common in mainstream programming. The concept of "extension points" is known in plugin systems, but the syntax is new.
- **Ordering matters for effects**: If two concurrent contexts fill the same slot, their `[on_entry]` effects may fire in an undefined order. The verifier must enforce ordering rules (see Consequences section).
- **Recursive slots not allowed**: A `fills` block cannot itself declare `slot`s. This simplifies verification but limits composition depth in the v0.0.1 specification.

---

## Alternatives considered

1. **Pure DCI with implicit role injection**: Rejected. This would require the system to infer which contexts apply which roles based on context topology, recreating the implicit-conditionals problem.

2. **Parameter-based overlays**: `context ModalComentario(with_sesion: bool)`. Rejected. This explodes the context space and makes contexts harder to reason about.

3. **Aspect-oriented roles** (weave roles at runtime): Rejected. Weaving is a dynamic mechanism; Trenza requires static verification.

4. **Separate "extension context" type**: Rejected. Creating a new context type for this purpose adds syntactic surface without benefit.

---

## Relation to other ADRs

- **ADR-001** (Trenza is a DSL): The `slot`/`fills` mechanism is how Trenza makes composition explicit, supporting ADR-001's goal of making state machines transparent.
- **ADR-010** (Three explicit context types): `slot`/`fills` is the mechanism that allows concurrent and overlay contexts to interact.
- **ADR-014** (One action per handler): Roles added via `fills` follow the same constraint: one action per handler.
- **Future ADR** (Conflict resolution): When multiple concurrent contexts fill the same slot, a conflict-resolution rule must be established in `system.trz`.
