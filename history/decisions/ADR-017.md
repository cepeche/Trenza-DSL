# ADR-017: Four Strands: multi-artifact synthesis from specification

**Status**: Accepted  
**Date**: 2026-03-20  
**Source**: `history/chronicle/2026-03-20/05-propuesta-estructura-v001.md`, `history/chronicle/2026-03-24/01_opus_diseno_strand2_tests.md`  
**Related**: ADR-001 (DSL principles), ADR-019 (`@intent` annotation)  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Gemini 2.5 Pro, Lead Developer

---

## Context

Trenza's founding metaphor (ADR-004) is the **three-strand braid**: specification, implementation, and tests are complementary artifacts. However, as the design matured, a fourth artifact emerged: **requirements documentation** (the inverse of the specification — what the human asked for, reconstructed from design traces).

These four artifacts are synthesized from a single `.trz` specification in parallel:

1. **Strand 1** — Implementation (Rust, TypeScript, Go)
2. **Strand 2** — Tests (algebraic, effect-based)
3. **Strand 3** — Schematics (state diagrams, Mermaid)
4. **Strand 4** — Requirements (audit trail, compliance documentation)

Each strand is generated independently but coherently from the same AST, ensuring consistency and eliminating the "specification drift" problem.

---

## Decision

The Trenza compiler generates **four independent strands** from each specification.

### Strand 1: Implementation

**Outputs**: `_out.rs` (Rust), `_out.ts` (TypeScript, future), etc.

**Content**:
- Role handler functions (event dispatchers)
- State machine logic (transitions, guards)
- Effect invocations (side effects)
- Type definitions (serializable data structures)

**Invariant**: Compiles without errors; can be linked with hand-written externals; supports zero-cost abstractions.

### Strand 2: Tests

**Outputs**: `_out_tests.rs` (algebraic test suite)

**Content**:
- One test per (context × role × event) combination
- Effect mocking via `Effects` trait with `NoOpEffects` fallback
- Verification that all handlers, transitions, and guards execute
- Coverage is **complete by construction** — no test selection required

**Framework**: Rust `#[test]` with zero external dependencies (no proptest, quickcheck, or heavyweight frameworks).

### Strand 3: Schematics

**Outputs**: `_out.mermaid` (state diagrams), `_out.html` (interactive visualization, future)

**Content**:
- State machine topology (contexts, transitions)
- Role and event cardinality
- Guard conditions (as labels on edges)
- Slot/fills composition visualized as overlays

**Purpose**: Human comprehension; auditable proof that the specification matches intent.

### Strand 4: Requirements

**Outputs**: `_out_audit.md` (narrative compliance document)

**Content**:
- Elements marked with `@intent` (ADR-019) expanded into natural language requirements
- Traceability matrix: each requirement → implementation elements
- Effects list with audit annotations
- Security properties (RGPD data flows, immutability constraints)

**Purpose**: Compliance documentation, user acceptance criteria, traceability for regulated systems.

## Synthesis process

```
.trz source
    ↓
[Parser] → AST (JSON)
    ↓
[Validator] → Verification results (8 rules)
    ↓
┌─────────────────────────────────────────┐
│  AST → Generators (parallel execution)  │
├─────────────────────────────────────────┤
│  Strand 1 → Implementation code          │
│  Strand 2 → Test code                    │
│  Strand 3 → Diagrams                     │
│  Strand 4 → Audit trail                  │
└─────────────────────────────────────────┘
    ↓
[Package] → .tzp (ZIP with manifest)
```

All four generators consume the **same AST**, ensuring consistency.

---

## Consequences

### Positive

- **Specification is ground truth**: No separate documentation, tests, or diagrams to maintain. All are derived.
- **Coherence guaranteed**: A change in the specification automatically updates all four strands.
- **Complete verification**: Strand 2 (tests) proves the specification is internally consistent; Strand 1 (code) proves it is executable; Strand 3 (diagrams) proves it is understandable; Strand 4 (requirements) proves it meets user intent.
- **Audit trail**: Requirements (Strand 4) trace back to implementation (Strand 1) and tests (Strand 2), satisfying compliance requirements.
- **Reduced cognitive load**: Developers don't maintain separate specs, code, tests, and docs — they maintain one artifact.

### Negative / constraints

- **Generator complexity**: The compiler must implement four independent generators, each with its own verification and output format.
- **Debugging generated code**: Errors in Strand 1 (implementation) can be harder to diagnose because the code is generated, not hand-written.
- **Strand 2 overhead**: Generated tests are verbose. Test frameworks must handle hundreds or thousands of test functions per specification.
- **No partial generation**: If one generator fails, the entire synthesis fails. There's no graceful degradation (e.g., "generate Strand 1 only").

---

## Alternatives considered

1. **Single artifact** (implementation only): Rejected. Tests and documentation decay without specification as source of truth.

2. **Three strands** (no Strand 4): Rejected. Compliance-critical systems need an auditable requirements trail.

3. **Sequential generation** (Strand 1 generates Strand 2, etc.): Rejected. This creates indirect dependencies; changes to Strand 2 logic would require updating Strand 1 first.

4. **Pluggable generators**: Support only the generators needed for a project. Rejected for v0.0.1; all four are required for full value.
