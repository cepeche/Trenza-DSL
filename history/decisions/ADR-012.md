# ADR-012: Plain JSON manifest for `.tzp` packages

**Status**: Accepted  
**Date**: 2026-03-12  
**Source**: `history/chronicle/2026-03-12/02-decisiones-pendientes-claude.md` + `03-decisiones-pendientes-opus.md`  
**Related**: ADR-011 (Python prototype), ADR-003 (One file per context)  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Lead Developer

---

## Context

Trenza projects are distributed as **packages** (`.tzp` files) — essentially ZIP archives containing:
- `.trz` source files
- Generated code and diagrams
- Metadata about the package

The question was: **what format should the metadata manifest use?**

Two options emerged:

1. **OPC (Open Packaging Conventions)**: The standard used by `.docx`, `.xlsx`, and other Microsoft Office formats. XML-based, comprehensive, battle-tested.
2. **Custom JSON schema**: Simple, lightweight, designed specifically for Trenza's needs.

OPC is powerful but was designed for a different ecosystem (document composition). Adapting it to Trenza would require translating XML to JSON, adding unnecessary complexity. However, OPC embodies two valuable principles:

- The `mimetype` file is stored uncompressed at the start of the ZIP, allowing format identification without full decompression.
- A central manifest in the archive root declares all parts and their relationships.

The decision: adopt OPC's *principles* in a simpler JSON-based schema, rather than the OPC standard itself.

---

## Decision

The `.tzp` (Trenza package) format uses **plain JSON** for its manifest.

### Package structure

```
my-project.tzp/
├── mimetype              -- uncompressed, identifies format
├── manifest.json         -- package metadata (not compressed in v0.x)
├── trenza/               -- source .trz files
│   ├── system.trz
│   ├── data.trz
│   └── contexts/
├── generated/            -- generated artifacts
│   ├── impl/             -- implementation code
│   ├── tests/            -- test code
│   └── docs/             -- documentation
└── .signatures/          -- optional: cryptographic hashes (v1.0+)
```

### Manifest schema (v0.0.1)

```json
{
  "manifest_version": "0.1",
  "trenza_version": "0.1.0",
  "name": "MyProject",
  "description": "A Trenza specification example",
  "version": "1.0.0",
  "author": "Developer Name",
  "license": "AGPL-3.0",
  "system": "trenza/system.trz",
  "data": "trenza/data.trz",
  "contexts": [
    {
      "path": "trenza/contexts/ModoNormal.trz",
      "sha256": "a7f8b9c2d3e4f5g6h7i8j9k0l1m2n3o4"
    },
    {
      "path": "trenza/contexts/ModoEdicion.trz",
      "sha256": "c3d2e1f0g9h8i7j6k5l4m3n2o1p0q9r8"
    }
  ],
  "externals": [
    {
      "path": "trenza/external/cronometro_api.trz",
      "sha256": "e5f4g3h2i1j0k9l8m7n6o5p4q3r2s1t0"
    }
  ],
  "generated": {
    "implementation": {
      "rust": "generated/impl/sistema.rs",
      "typescript": "generated/impl/sistema.ts"
    },
    "tests": "generated/tests/sistema_test.rs",
    "docs": "generated/docs/index.md",
    "diagrams": "generated/diagrams/state-diagram.mermaid"
  }
}
```

### Key fields

| Field | Purpose | Required |
|-------|---------|----------|
| `manifest_version` | Manifest schema version (not Trenza version) | Yes |
| `trenza_version` | Trenza language version used to generate | Yes |
| `name` | Human-readable project name | Yes |
| `version` | Semantic versioning of the package | Yes |
| `system` / `data` | Primary specification files | Yes |
| `contexts` | All context `.trz` files with SHA256 | Yes |
| `externals` | All external module definitions | Yes |
| `generated` | Paths to all generated artifacts | No (for source-only packages) |

### Mimetype file

The file `mimetype` contains a single line:

```
application/trenza-package
```

This is stored **uncompressed** at the start of the ZIP, allowing tools to identify the format without decompressing the entire file.

## Consequences

### Positive

- **Simplicity**: JSON is human-readable, easy to parse, and widely supported.
- **Flexibility**: New fields can be added to the schema without breaking existing parsers (backward compatibility).
- **Lightweight**: No XML verbosity or complex nesting.
- **Trenza-specific**: The schema is designed for Trenza's actual needs, not a general-purpose format.
- **Verifiable content**: SHA256 hashes allow validation of package integrity (important for compliance, ADR-006 motivations).

### Negative / constraints

- **Less mature than OPC**: OPC is battle-tested across millions of Office files. Trenza's custom format is new and may discover edge cases.
- **No standardization yet**: No JSON Schema validation file exists. Parsers must implement validation manually (v0.0.1 limitation).
- **No encryption or signatures** (v0.0.1): OPC supports embedded signatures for authenticity. Trenza defers this to v1.0 (`.signatures/` directory is reserved but not implemented).

---

## Alternatives considered

1. **Adopt OPC fully**: Rejected. XML adds complexity for a domain (Trenza packages) where JSON is more natural.

2. **Use TOML instead of JSON**: Rejected. TOML is human-friendly but less standard for programmatic access. JSON is more widely supported.

3. **Use a single `.manifest.toml` file with a different structure**: Rejected. JSON is more suitable for hierarchical data (nested `generated` field).

4. **YAML for manifest**: Rejected. YAML is less suitable for package distribution (security parsing vulnerabilities in some implementations).

5. **Embed manifest in a `.trz` file instead of separate JSON**: Rejected. A separate manifest file allows tools to inspect packages without parsing Trenza grammar.

---

## Future extensions

### v1.0 additions

1. **JSON Schema validation** — publish `manifest.schema.json`
2. **Signature support** — `.signatures/package.sig` for cryptographic verification
3. **Dependency resolution** — `dependencies` field for declaring external `.tzp` packages
4. **Distribution metadata** — `repository` field for package registry URLs

These do not change the core structure; they extend it backward-compatibly.

## Relation to other ADRs

- **ADR-011** (Python prototype): The Python compiler v0.0.1 generates and validates manifest files in this format.
- **ADR-003** (One file per context): Each `.trz` context gets an entry in the `contexts` array with its SHA256 hash.
- **Future ADR** (Package distribution and dependencies): This ADR establishes the base format that dependency resolution will build upon.
- **Compliance and security**: The SHA256 hashes support audit trails required for regulated systems (ADR-006 motivations).
