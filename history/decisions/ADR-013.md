# ADR-013: Implicit inheritance in contexts

**Status**: Accepted  
**Date**: 2026-03-12  
**Source**: `history/chronicle/2026-03-12/03-decisiones-pendientes-opus.md`; also referenced in `history/decisions/ADR-014.md`  
**Related to**: ADR-010 (context types), ADR-014 (one action per handler)  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Lead Developer

---

## Context

When contexts are nested (a child context specializing a parent context), the question arises: **must a child context re-declare all roles from the parent, or can roles be inherited implicitly?**

For example, in CronometroPSP:
- `ModoNormal` has a role `pestaña_actividades` with handler `on tap -> mostrarActividades`
- `ModoEdicion` is a child of `ModoNormal`, inheriting the same role and its behavior
- But `ModoEdicion` adds new roles specific to editing (e.g., `campo_nombre`, `boton_guardar`)

The alternative would require:

```trenza
-- BAD: verbose re-declaration
context ModoEdicion:
    role pestaña_actividades: Pestaña  -- re-declared
        on tap -> mostrarActividades   -- re-declared

    role campo_nombre: CampoTexto
        on cambio -> actualizarNombre(self.valor)
```

This is unnecessarily verbose. The lexical scoping analogy (a nested function inheriting the outer scope's variables) suggests that roles should inherit implicitly. However, there are precise rules needed to make inheritance safe for verification.

---

## Decision

Roles in a child context are **implicitly inherited** from the parent context unless explicitly overridden.

### Three inheritance rules (H1–H3)

#### H1: Role visibility

A role declared in the parent context is visible in the child context without re-declaration.

```trenza
context ModoNormal:
    role pestaña_actividades: Pestaña
        on tap -> mostrarActividades

context ModoEdicion:
    -- pestaña_actividades is inherited and visible here
    
    role campo_nombre: CampoTexto
        on cambio -> actualizarNombre(self.valor)
```

#### H2: Role override (explicit re-declaration)

A child context can **override a parent role's handlers** by re-declaring the role in full:

```trenza
context ModoEdicion:
    role pestaña_actividades: Pestaña  -- override: declare in full
        on tap -> mostrarAyudaEdicion(self.id)  -- different handler
    
    role campo_nombre: CampoTexto
        on cambio -> actualizarNombre(self.valor)
```

If a role is mentioned in the child context, it **must be fully re-declared**. Partial redeclaration (e.g., listing the role name without handlers) is a syntax error. This prevents ambiguity: "if I mention a role, am I saying 'use the parent's handlers' or did I forget to write handlers?'"

#### H3: Role isolation between siblings

Sibling contexts do not share roles. If `ModoEdicion` declares `campo_nombre: CampoTexto` and `ModoNormal` declares a different `campo_nombre: CampoTexto`, they are **independent local roles**, not the same inherited role.

```trenza
context ModoNormal:
    role campo_nombre: CampoTexto
        on cambio -> validarNombre(self.valor)

context ModoEdicion:
    role campo_nombre: CampoTexto  -- independent local role
        on cambio -> actualizarNombre(self.valor)  -- different handler
```

The completeness rule (ADR-001) applies **per context**, not across the inheritance tree.

---

## Consequences

### Positive

- **Less verbosity**: Child contexts only declare what's new or different, not the entire inherited interface.
- **Natural scoping**: The lexical scoping analogy (nested functions seeing outer scope) is intuitive and matches mental models from other languages.
- **Modular change**: If a parent role changes, all children inherit the change automatically. No manual propagation.

### Negative / constraints

- **Hidden dependencies**: A child context's behavior depends on the parent context's role declarations, which may not be visible in the same file (per ADR-003).
- **Ambiguity in visual debugging**: When reading a `.trz` file for a child context, one must know which roles come from the parent. The `trenza inspect` tool (future) should make this explicit.
- **No partial override**: A child cannot change the **event catalog** of an inherited role (see discussion on handler extension below). It must re-declare the role in full or declare a new local role.

---

## Handler extension is forbidden

A child context **cannot add new event handlers to an inherited role**. The event catalog of a role must be stable across the inheritance hierarchy.

### Why?

If a parent role `pestaña_actividades` responds to `on tap` but a child role adds `on doble_tap`, then:

```trenza
-- FORBIDDEN:
context ModoEdicion:
    role pestaña_actividades: Pestaña  -- re-open the parent's role
        on doble_tap -> mostrarOpciones  -- add a new handler
```

This violates the **Completeness rule**: the catalog of events for `pestaña_actividades` becomes context-dependent. An audit tool asking "what events does `pestaña_actividades` handle?" would get different answers depending on the context level.

### The alternative: local roles

Instead, declare a new local role:

```trenza
context ModoEdicion:
    role pestaña_edicion: Pestaña
        on doble_tap -> mostrarOpciones  -- local role for new behavior
```

This keeps role catalogs stable and uses existing language constructs (local roles) instead of creating an exception (event extension).

---

## Alternatives considered

1. **No inheritance; always re-declare**: Rejected. This defeats the purpose of having a hierarchy. Verbosity would be high.

2. **Implicit inheritance + allow handler extension**: Rejected. This breaks the stability of role event catalogs and complicates verification.

3. **Explicit `extends` keyword**: Rejected for v0.0.1. Implicit inheritance with lexical scoping is clearer. If future versions need explicit control, an `extends` keyword can be added without breaking existing code.

4. **Mixin-based composition instead of inheritance**: Rejected. Mixins are more powerful but also more complex. For a v0.0.1 specification, implicit role inheritance is the right level of abstraction.

---

## Relation to other ADRs

- **ADR-010** (Three context types): Base contexts are parents; overlays and concurrent contexts can be children, inheriting roles.
- **ADR-014** (One action per handler): Role inheritance does not affect this constraint. Each handler (whether inherited or local) must emit exactly one action.
- **ADR-020** (Contract between actions and state machine): Role inheritance works because the contract (role → action → event → transition) is per-context, not per-hierarchy.
- **Future ADR** (Context composition patterns): More advanced patterns (mixins, traits, role delegation) may be explored after v0.0.1.
