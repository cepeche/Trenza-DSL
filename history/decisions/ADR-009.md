# ADR-009: Repository structure for v0.0.1

**Status**: Accepted  
**Date**: 2026-03-20  
**Source**: `history/chronicle/2026-03-20/05-propuesta-estructura-v001.md`  
**Related**: ADR-003 (One file per context)  
**Participants**: Claude Opus 4.6, Claude Sonnet 4.6, Gemini 2.5 Pro, Lead Developer

---

## Context

The Trenza project has two distinct audiences and two distinct products:

1. **The Trenza language specification** — the grammar, semantics, verification rules, and tools
2. **The design process** — how three LLMs and a human collaboratively designed a language

Early attempts to structure the repository mixed these concerns. Documentation was scattered; decision rationale was buried in chat logs; the specification was not clearly distinguished from examples.

Trenza's founding principle (ADR-001) is that specification is the primary artifact. Everything else is derived. The repository structure should reflect this hierarchy and make both the specification and the process auditable to external researchers.

---

## Decision

The repository is restructured with five top-level directories, each serving a distinct purpose:

### 1. `spec/` — Specification and reference implementation

```
spec/
├── language/              -- Formal definition of the Trenza language
│   ├── 01-overview.md     -- What, for whom, why
│   ├── 02-grammar.md      -- Complete grammar
│   ├── 03-verification.md -- Verification rules
│   ├── 04-package-format.md
│   └── 05-cli.md
│
└── reference/             -- Canonical reference implementation
    └── cronometro-psp/    -- CronometroPSP (the founding use case)
        ├── trenza/        -- .trz specification files
        ├── app/           -- Generated/hand-written application
        └── tests/         -- Test suite
```

**Purpose**: The specification IS the primary artifact. Everything in `spec/language/` is normative. `spec/reference/` contains the canonical example that demonstrates the specification is executable.

### 2. `docs/` — User-facing documentation and design rationale

```
docs/
├── manual/                -- User manual
├── generated/             -- Documentation auto-generated from .trz files
└── design/                -- Design principles, influences, and decisions (published)
```

**Purpose**: Documentation for developers using Trenza. Includes:
- The Trenza manual (how to write `.trz` files)
- Auto-generated documentation from reference implementations
- Design rationale (influences, security principles, lifecycle)

### 3. `history/` — Auditable design process

```
history/
├── chronicle/             -- Day-by-day memos from all participants
│   ├── 2026-03-04/       -- One directory per calendar date
│   ├── 2026-03-05/
│   └── ...
├── decisions/             -- ADR-format decision records (this file)
├── inspirations/          -- Comparative analysis of related work
└── meta/                  -- Reflections on the design process
```

**Purpose**: Make the design process transparent and auditable. This is research material; external researchers can trace how requirements emerged, alternatives were evaluated, and decisions were made. The chronicle is primarily in Spanish (project origin); ADRs are in English (publication language).

### 4. `src/` — Compiler and tools (implementation)

```
src/
└── trenza/                -- Python prototype (v0.0.1 only)
    ├── parser.py
    ├── verifier.py
    ├── docgen.py
    ├── mermaid.py
    └── cli.py
```

**Purpose**: The compiler implementation. For v0.0.1, this is a Python prototype for rapid iteration. Will be rewritten in Rust for v1.0 (see ADR-011).

### 5. `.agents/` — LLM automation and workflows

```
.agents/
└── workflows/
    └── session-closure.md  -- Automated session-end procedures
```

**Purpose**: Configurations for autonomous LLM agents to support project maintenance (future).

## Naming conventions

### Chronicle files

Each file in `history/chronicle/YYYY-MM-DD/` follows the pattern:

```
NN_AUTHOR_descriptive-title.md
```

Examples:
- `01_CL_briefing-para-gemini.md` — Claude Sonnet (CL) briefing document
- `02_GE_infraestructura-completa.md` — Gemini (GE) infrastructure proposal
- `03_CO_cimbra-vision.md` — Claude via Cowork/Dispatch (CO) vision document

Author codes (from ADR-021):
- `CL` — Claude (via Claude Code or IDE extensions)
- `GE` — Gemini (any interface)
- `CO` — Claude via Dispatch/Cowork (occasional)
- `CX` — Reserved for future collaborators

### Decision records

Each ADR is a separate file: `ADR-NNN.md`. No additional naming is needed; the sequential number and title are sufficient.

## Consequences

### Positive

- **Hierarchy is clear**: Specification is top-level (`spec/`); tools are secondary (`src/`); documentation follows.
- **Process is auditable**: External researchers can read the chronicle and understand how decisions were made.
- **Scalability**: As the project grows, new tools (Rust compiler, LSP, WASM builds) have a clear home (`src/trenza-rust/`, etc.).
- **Separation of concerns**: Users need `spec/` and `docs/`; developers need `src/`; researchers need `history/`.

### Negative / constraints

- **More directories**: The repository has 5 top-level directories instead of 3. This can be overwhelming for first-time contributors.
- **Chronicle organization by date**: Finding a specific memo requires knowing its approximate date. An index in `history/chronicle/README.md` helps, but it's not a full-text search.
- **Maintenance burden**: Keeping `history/` organized and indexed requires discipline from the team.

---

## Alternatives considered

1. **Flat structure** (keep everything in one `docs/` directory): Rejected. Fails to distinguish the specification (normative) from documentation (descriptive).

2. **Traditional project layout** (no `history/`): Rejected. The design process is a research artifact and deserves preservation.

3. **Chronicle indexed by topic, not date** (e.g., `history/design-decisions/`, `history/compiler-development/`): Rejected. Decisions don't map cleanly to topics; topic-based organization requires retroactive categorization. Date-based organization is immutable and authentic.

4. **Merge `spec/language/` and `docs/design/`**: Rejected. Specification (normative, frozen) and design rationale (descriptive, evolving) serve different audiences. Keeping them separate is clearer.
