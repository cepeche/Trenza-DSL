**Date**: 2026-04-16 (original proposal: 2026-03-20)

---

## Context

A `.trz` file is semantically opaque with respect to the **provenance** of each
element. Given the specification of a system — a `system` block, its contexts,
their roles, transitions and effects — there is no way to tell which elements
were explicitly requested by the user during the dialogue (Strand 0) and which
were added by the model as technical scaffolding required for the specification
to be complete and verifiable.

Both categories are necessary. But they are not the same:

- **Intent**: what the user consciously asked for.
- **Derivation**: what the model added to make the intent viable within the
  constraints of the DSL.

Without a way to distinguish them, Strand 4 (the Fourth Strand, ADR-017) cannot
generate a requirements document that reflects user intent — it can only produce
a technical paraphrase of the whole AST. That defeats the purpose: Trenza's
differentiating claim is that requirements are **a projection of the specification**
rooted in the author's intent, not a restatement of the code.

`@intent` is the mechanism that makes that projection well-defined.

### Why this ADR is being ratified now, not in March 2026

The original proposal was drafted on 2026-03-20 and filed as ADR-019 in
"Proposed" state during the consolidation of v0.0.1. It was never ratified
because the project's implementation focus shifted to ADR-020 (identity),
ADR-021 (public surface and reuse) and ADR-022 (name–hash validation). Four
circumstances of the March proposal are now obsolete and are corrected in this
ADR (see §4 below):

1. The implementation language (Python → Rust).
2. The grammar vocabulary (`state` → `context`, since Trenza has no `state`
   keyword; what the March text called "state" is a Trenza context in the
   current grammar).
3. The version calendar (`v0.0.1` / `v0.1`) — no longer applicable.
4. The relationship to sister decorators (`@audit`, `@decision`) — these were
   introduced later and must be addressed explicitly.

## Decision

### 1. Syntax

Four forms, all legal:

| Form | Meaning |
|------|---------|
| *(no annotation)* | Element is derived (default). |
| `@intent` | Element is confirmed intent, without free-text formulation. |
| `@intent("text")` | Element is confirmed intent, with a natural-language formulation. |
| `@intent("text", source: "path")` | Intent with a reference to the Strand 0 entry or chronicle where it was confirmed. |

The grammar already accepts the decorator form via the existing rule used for
`@audit` (see `spec/language/02-grammar.md`, line 245). `@intent` reuses that
rule verbatim. No new grammar production is introduced.

### 2. Elements that can carry `@intent`

Mapped onto the current AST nodes (`trenza-core/src/ast.rs`):

| AST node | Grammar construct | Rationale |
|----------|-------------------|-----------|
| `ContextDef` | `context X:` | A context in Trenza is a use case (Reenskaug DCI). It is the natural unit of intent: "the user can do X". |
| `RoleDef` | `role x: T` (inside a context) | A role answers "who participates"; intent may exist at this granularity. |
| `TransitionRule` | `on event -> TargetContext` | Transitions between contexts are typically user-visible flow decisions. |
| Role action | `on event -> action(...)` inside a role | The most common grain of intent. Already carries decorators today. |
| `EffectRule` | inside `effects:` | When an effect is intent-driven (e.g. "every sale must be logged to accounting"). |
| `DataDef` / `DataField` | `data X:` / `field: T` | Data is intent when its existence responds to a user requirement (e.g. an auditable field required by the domain). |
| `ExternalDef` | `external M:` | Intent-driven when the external dependency itself is a user requirement. |

Elements that **cannot** carry `@intent`:

| AST node | Rationale |
|----------|-----------|
| `SystemDef` | The system as a whole is not an individual requirement. |
| `ImportDef` | Imports are composition mechanism, not intent. |
| `SlotDef` / `FillsDef` | Slots and fills are composition (ADR-021), not intent. |
| `EnumDef` | Enumerations are structural; intent lives on the data field that uses the enum, not on the enum itself. |

This list **diverges** from the March 2026 proposal on one point: the March text
said contexts were "too coarse" to be anotable. That was written when the
proposal was using `state` as the unit of specification. In the current grammar,
a context **is** the Trenza analogue of a DCI use case, which is exactly the
grain at which user intent is expressed. Contexts are now explicitly anotable.

### 3. Semantics

- **`@intent` is optional.** A `.trz` without any `@intent` is valid. The verifier
  does not require it. The CLI may emit an informational notice about coverage.

- **`@intent` is not heritable.** Annotating a context does not propagate the mark
  to its roles, transitions, effects or data. Each element is annotated individually.
  Rationale: "the user asked for this use case" does not mean "the user asked for
  every transition inside it". Granularity forces precision.

- **`@intent` is immutable post-confirmation.** Once the user confirms an `@intent`,
  the model should not delete it or reformulate its text without explicit
  confirmation. This is a **process** guard, not a language guard — the verifier
  does not enforce it. The CLI may warn about deletions or reformulations via
  `trenza intent-diff`.

- **Shared free text aggregates.** When two or more elements carry `@intent` with
  the same free-text formulation, they are grouped under one requirement in the
  generated Strand 4 document.

### 4. Traceability into generated code

**Decision**: `@intent` does **not** propagate into the generated Rust, WASM,
Mermaid or tests. Generated code is a functional projection; intent metadata
belongs to a parallel artifact.

The compiler emits, as a separate output of Strand 4, a **traceability map**:

```
<package>.tzp/
  generated/
    impl/
    tests/
    schematics/
  traceability/
    intent-map.json         ← new artifact (Strand 4)
    requirements.md         ← generated document (ADR-017)
```

`intent-map.json` contains, for every `@intent`-annotated AST node:

- Source span in the `.trz`.
- Free text and optional `source:` reference.
- Corresponding symbols in generated Rust (fully qualified path).
- Corresponding test cases (if the element produces tests).
- Corresponding Mermaid element identifier (if it appears in a diagram).

This answers the open concern from the 2026-04-16 dialogue:

> "Where I don't see it being needed is in the generated code, with one
> possible exception: an external audit of the code that allows pinpointing
> exactly which user request a specific code section responds to."

The audit need is met without contaminating generated code. The map is
machine-readable and signed alongside the `.tzp` manifest (ADR-020).

### 5. Relationship to sister decorators

The decorator family introduced via `docs/design/decorators-decision-violation-strand0.md`
is orthogonal by design. The three decorators answer three different questions,
may coexist on the same element, and have different compilation profiles:

| Decorator | Question answered | Survives `--profile=pro` | Generates code |
|-----------|-------------------|-------------------------|----------------|
| `@audit("reason")` | Why does this event matter legally? | Yes | Yes (audit hook) |
| `@intent("text")` | Is this a confirmed requirement or scaffolding? | No | No |
| `@decision("ADR-NNN")` | Which ADR justifies this declaration? | Yes (in Strand 4) | No (metadata only) |

A single element may carry all three:

```trenza
@intent("Legal requirement: immutable cancellation log")
@decision("ADR-012")
@audit("Legal: cancellation record")
on cancel -> cancelOrder(self.id)
```

The decorator grammar rule is shared. The semantics diverge in the compiler.

### 6. CLI surface

These commands are part of the CLI contract but their implementation schedule
is separate from this ADR. They are listed here because they define the
observable behaviour of `@intent`:

```bash
trenza requirements <pkg>.tzp --format markdown    # Strand 4 projection
trenza intent-coverage <pkg>.tzp                   # coverage percentage
trenza intent-diff <rev>..<rev>                    # intent-level diff between revisions
trenza intent-sources <pkg>.tzp                    # validate source: references
trenza trace <pkg>.tzp --from-intent "<text>"      # intent → code map
```

## Implementation notes

1. **AST.** The current `ast.rs` already carries `annotations: Vec<(String, String)>`
   on `DataDef`, `ExternalDef` and `SlotDef`. `@intent` reuses this field with
   the key `"intent"`. The remaining AST nodes that must become anotable
   (`ContextDef`, `RoleDef`, `TransitionRule`, `EffectRule`, `DataField`) need
   the same field added. This is additive — no existing field changes type.

2. **Parser.** The existing decorator production accepts `@ident ( string )`. No
   grammar change is required; only the set of AST nodes on which the parser
   attaches decorators expands.

3. **Validator.** The validator must reject two malformations:
   - `@intent` on a disallowed node (see §2).
   - `@intent(source: "...")` whose `source` path does not refer to a file
     under `history/chronicle/` — this is a warning, not an error, because the
     referenced chronicle may not yet exist at compile time.

4. **Strand 4 emitter.** Two artifacts:
   - `intent-map.json` (mandatory when any `@intent` is present).
   - `requirements.md` (the Strand 4 document as specified in ADR-017).

5. **Profile.** `@intent` is stripped in `--profile=pro` output. It survives in
   the `traceability/` directory of the `.tzp` package regardless of profile.

## Consequences

### Positive

- Strand 4 (ADR-017) becomes operational. Requirements can be generated as a
  projection of the intent-annotated subset of the AST, not as a paraphrase of
  the whole specification.
- External auditability of generated code is preserved via `intent-map.json`,
  without polluting generated sources.
- Aligns with the existing decorator infrastructure — no new syntax, no parser
  rewrite.

### Negative / residual

- The validator enforcement of the anotable-node list (§2) is new work. Until
  implemented, an `@intent` on a disallowed node will parse and be silently
  retained in `annotations`, producing no visible effect. This is acceptable
  transitional behaviour; the emitter simply ignores keys it does not recognise.
- The `intent-map.json` schema is defined in this ADR at the conceptual level
  but not formalised as JSON Schema. That formalisation belongs to a later
  Strand 4 implementation ADR.

---

## Alternatives considered

1. **Propagate `@intent` into generated Rust as a doc-comment or attribute.**
   Rejected. Generated code is a functional projection; polluting it with
   provenance metadata breaks the principle that generated artifacts are
   equivalent regardless of which tool produced them.

2. **Make `@intent` mandatory for every AST element.** Rejected. Forces the
   author to classify every element as intent-or-derivation, including trivial
   scaffolding where the distinction adds no value.

3. **Infer intent from Strand 0 automatically, without an in-source marker.**
   Rejected. Strand 0 is a rich, noisy record of dialogue; automatic inference
   would require NLP over the dialogue log and would never be as reliable as
   an explicit author mark.

---

## Open questions (deferred to implementation)

1. Should `@intent` admit a `priority:` argument (MoSCoW)? Default: no. Can be
   added as an extension without breaking this ADR.

2. Should the same element be allowed to carry `@intent` in one context and be
   derived in another (for contexts that reuse components via `use`)? The
   March proposal argued yes. This ADR defers to the `use` semantics in ADR-021.

3. Should the CLI offer an interactive annotator (`trenza annotate`)? This is
   tooling UX and is not part of the language contract.

---

**Closing note**: `@intent` is the piece that makes Strand 4 (the Fourth Strand,
requirements-as-projection) concrete and verifiable rather than aspirational.
It is specifically aligned with the project's differentiating claim: the
specification and the requirements are the same artifact, projected from
different angles. Without `@intent`, the projection onto requirements has no
principled source. With `@intent`, it does.
