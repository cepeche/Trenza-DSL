# ADR-018: Traceability of design decisions in multi-LLM collaboration

**Status**: Accepted  
**Date**: 2026-03-20 (recorded); principles evolved through March 26  
**Source**: Implicit in `history/chronicle/` structure and ADR-021; documented in practices  
**Related**: ADR-021 (Multi-Interface Claude Protocol), ADR-009 (Repository structure)  
**Participants**: Lead Developer, Claude Opus 4.6, Claude Sonnet 4.6, Gemini 3.1 Pro

---

## Context

The Trenza project is a novel collaboration: a human, Claude Sonnet, Claude Opus, and Gemini worked together to design a language. Decisions were made through dialogue, implemented by different agents in different sessions, and reviewed by others. The question arose: **how do we maintain a clear, auditable record of who decided what, when, and why?**

Without traceability:
- Design rationale is lost. Future contributors don't know why a decision was made.
- Responsibility is unclear. If a bug is discovered, tracing it back to its source becomes impossible.
- Collaboration patterns are hidden. The methodology itself (human-LLM co-design) is invisible to external observers, especially researchers.

The solution is to make the design process itself an artifact: every decision, memo, and implementation choice is recorded with authorship, date, and context.

---

## Decision

Design decisions are traced and recorded through a **structured chronicle** with explicit authorship, dating, and cross-referencing.

### 1. Chronicle organization by date

Daily entries in `history/chronicle/YYYY-MM-DD/` capture the design conversation:

```
history/chronicle/
├── 2026-03-04/          -- Concepto inicial, diseño
├── 2026-03-05/          -- Primeras rondas de diseño
├── ...
├── 2026-03-18/          -- GAP resolution sessions
├── 2026-03-20/          -- Estructura, propuestas
└── 2026-03-26/          -- MAPSE integration, multi-agent dispatch
```

**Benefit**: A researcher can read forward through the chronicle and see how ideas evolved in real time.

### 2. Authorship encoding in filenames

Each chronicle entry's filename encodes the intellectual author (ADR-021):

```
NN_AUTHOR_descriptive-title.md
```

Examples:
- `01_CL_briefing-para-gemini.md` — Claude (via Claude Code) authored a briefing for Gemini
- `05_GE_propuesta-estructura.md` — Gemini authored a structure proposal
- `10_CO_briefing-cimbra.md` — Claude (via Cowork/Dispatch, occasional coordinator role)

### 3. Cross-referencing ADRs to chronicle

Each ADR includes a **Source** field that points to the chronicle entries that informed it:

```markdown
**Source**: `history/chronicle/2026-03-18/06-memo-opus-resolucion-gap2.md`
```

This creates a bidirectional link: readers can trace from the decision record back to the dialogue that motivated it.

### 4. Traceability in implementation

When a chronicle entry proposes a code change, the proposal is referenced in commit messages:

```bash
git commit -m "Implement slot/fills mechanism

Based on memo 2026-03-20/03-resolucion-gap4-definitiva.md
See ADR-007 for formal decision."
```

This ties implementation to design rationale via git history.

### 5. Multi-agent session coordination

When multiple LLMs work on the same task (e.g., designing verification rules), handoff memos document the context:

```
BEFORE:    Claude Sonnet session ends with analysis of test generation
   ↓
HANDOFF:   Memo: "Opus, here's the context. Strand 2 needs algebraic testing..."
   ↓
AFTER:     Claude Opus session begins, reads memo, continues design
   ↓
OUTPUT:    Implementation draft, pushed to repo for Gemini to review
```

## Consequences

### Positive

- **Process transparency**: External researchers can understand how the language was designed.
- **Decision accountability**: Each decision is attributed; mistakes can be traced to their source.
- **Replication**: The methodology (human-LLM co-design) is documented and reproducible.
- **Collaboration patterns**: Future projects using this methodology can learn from our approach.
- **Historical record**: If the project is ever forked or disputed, the chronicle is an immutable audit trail.

### Negative / constraints

- **Information overload**: The chronicle can grow to thousands of files. Finding a specific decision requires knowing approximately when it was made.
- **Storage overhead**: Storing every memo (many are exploratory) increases repo size.
- **Privacy concerns**: If the project becomes public, internal design discussions may reveal business logic or strategic decisions the team wanted to keep confidential.
- **Organizational burden**: Maintaining consistent authorship encoding and cross-referencing discipline requires team agreement and vigilance.

---

## Alternatives considered

1. **No chronicle; decisions documented in ADRs only**: Rejected. ADRs record *what* was decided, not *how* the decision was made. The process is valuable research material.

2. **Central wiki or external documentation**: Rejected. Keeping the chronicle in the git repo makes it part of the version control history and immutable (subject to git's guarantees).

3. **Automated commit message generation** from chronicle entries: Rejected for v0.0.1. Manual linking is more honest — it captures cases where a memo influenced code but didn't directly cause it.

4. **Encrypted archive** (to preserve privacy while maintaining traceability): Rejected. Encryption defeats the purpose of transparency for researchers. Sensitive material is simply not put in the chronicle.

---

## Guidelines for use

### When to record a memo

Record a memo if it:
- Proposes a new design decision
- Analyzes alternatives to a known problem
- Documents a handoff between agents
- Captures a breakthrough or resolved disagreement
- Includes code examples or test cases

### When NOT to record a memo

Don't record:
- Routine implementation work (handled by git commits)
- Typos or minor edits
- Duplicate discussions (link to the original instead)

### Naming discipline

- **NN**: Two-digit sequence number within the day (01, 02, ..., 99)
- **AUTHOR**: Two-letter code (CL, GE, CO)
- **Title**: Kebab-case, descriptive, under 50 characters

Example: `05_GE_diseno-generador-strand2.md`
