# ADR-003: One file per context

**Status**: Accepted  
**Date**: 2026-03-04 (principle established); 2026-03-24 (validated by CronometroPSP)  
**Source**: `history/chronicle/2026-03-04/02-diseno.md`; validated in multi-file synthesis (Iteration 11)  
**Participants**: Lead Developer, Claude Opus 4.6, Claude Sonnet 4.6, Gemini 3.1 Pro

---

## Context

In ADR-001, Trenza establishes the context as the unit of specification — the smallest self-contained, verifiable piece. The question then becomes: **what is the physical packaging strategy?** Should a single `.trz` file contain multiple contexts, or should each context live in its own file?

Three considerations informed this decision:

1. **Modularity and parallel work**: If contexts live in separate files, multiple team members can edit different contexts simultaneously without merge conflicts. Each context is independently verifiable, so there is no need to load the entire system to check a single context.

2. **Cognitive load**: A single large file containing many contexts becomes hard to navigate. Each context is a complete use case. Splitting them makes each file easier to understand and reason about.

3. **Composition and reuse**: Some contexts are more abstract (base contexts in a hierarchy) and others are concrete (overlays or specialized states). Clear file boundaries make it obvious which contexts are dependencies and which are extensions.

Empirical validation came from the CronometroPSP project (March 2026), which consists of 18 `.trz` files organized as:
- 2 base contexts (ModoNormal, ModoEdicion)
- 1 concurrent context (SesionActiva)
- 10 overlays (ModalComentario, ModalCrearTarea, etc.)
- 5 external module definitions

The multi-file synthesis implementation (Iteration 11 of the compiler) confirmed that the compiler can handle this structure seamlessly: dependencies are resolved, and verification rules apply across file boundaries as if the files were concatenated.

---

## Decision

Each **context** is defined in its own `.trz` file. The filename matches the context name (e.g., `ModoEdicion.trz` contains the `ModoEdicion` context).

### File naming convention

```
context_name.trz  →  CamelCase, exact match with the context declaration
```

Examples from CronometroPSP:
```
ModoNormal.trz
ModoEdicion.trz
SesionActiva.trz
ModalComentario.trz
ModalCrearTarea.trz
```

### External modules

External module definitions (which are not contexts but interfaces) are grouped in a single file per module family:

```
external_tipo_api.trz   (e.g., autenticacion_api.trz)
external_storage.trz
```

### Single specification per context

A `.trz` file contains **exactly one context definition**. Other elements (imports, type declarations used by that context) may appear in the same file for convenience, but the context is the primary unit.

---

## Consequences

### Positive

- **Parallel development**: Multiple developers can edit different contexts without waiting for locks or resolving file-level merge conflicts.
- **Easier review**: Code reviewers can reason about a single context in one file, rather than scanning a 500-line megafile.
- **Clear dependency graph**: The imports at the top of each `.trz` file make dependencies explicit. Tools can visualize which contexts depend on which.
- **Modular testing**: Each context can be tested in isolation by providing mock implementations of its external dependencies.
- **Dynamic loading**: In a WASM deployment, contexts can be compiled as separate modules and loaded on demand, reducing initial bundle size.

### Negative / constraints

- **More files to manage**: A large system (100+ contexts) creates many files. Tools and IDEs must support quick navigation (fuzzy search, outline views).
- **Implicit composition**: A system's behavior emerges from interactions between contexts, which can span many files. Developers must understand this composition. A single megafile makes composition explicit visually.
- **File order does not matter** (due to multi-file synthesis), but this can confuse developers who expect a linear reading order. Documentation must clarify the composition.

---

## Alternatives considered

1. **One large `.trz` file per application**: Rejected. This defeats the modularity benefits. A 1000-line file is hard to navigate and difficult to work on collaboratively.

2. **No prescribed convention; let users organize files as they prefer**: Rejected. This would create incompatibility across projects and make IDE support harder. A consistent convention is worth the constraint.

3. **Group related contexts by domain** (e.g., `authentication/login.trz`, `authentication/logout.trz`): Rejected. Directories add a layer of indirection. The filename should match the context name exactly, making it easy to jump to a context by name.

4. **One file, multiple contexts, explicit boundaries** (e.g., `sections:` or `---`): Rejected. This provides no benefits over directories and is harder to parse and reason about.

---

## Relation to other ADRs

- **ADR-001** (Trenza is a DSL): Contexts are the unit of specification. This ADR defines their physical packaging.
- **ADR-010** (Three explicit context types): Base, Concurrent, and Overlay contexts are each placed in their own files, but grouped logically in a directory structure (per team convention, not enforced by the language).
- **ADR-021** (Protocol for Multi-Interface Claude Participation): Multi-file synthesis ensures that concurrent edits by multiple LLMs or developers remain coherent.
- **Future ADR** (Package management): The `.tzp` (Trenza package) format will define how sets of `.trz` files are distributed and versioned.
