# ADR-002: Target: Rust + WASM

**Status**: Accepted  
**Date**: 2026-03-04 (original decision); confirmed 2026-03-24 as long-term strategic target  
**Source**: `history/chronicle/2026-03-04/02-diseno.md`  
**Participants**: Lead Developer, Claude Opus 4.6, Claude Sonnet 4.6, Gemini 3.1 Pro

---

## Context

Trenza needed a code-generation target that could satisfy multiple constraints simultaneously:

1. **Type safety and exhaustiveness checking**: The compiler must catch errors that would otherwise be runtime failures. This rules out dynamically typed languages.
2. **Performance in constrained environments**: The initial use case (CronometroPSP, a Pomodoro timer for personal task management) must run smoothly on mobile devices with limited CPU and memory.
3. **Multi-platform reach**: The same specification must compile to both server-side code (for APIs and business logic) and client-side code (for web and mobile UIs).
4. **Formal verification potential**: The long-term vision includes formal verification of generated code. This requires either a language with dependent types or a language that can interface cleanly with formal-verification tooling.
5. **Self-hosting**: The Trenza compiler itself should be written in Trenza (or a similar principled language) eventually. This requires the target language to be capable of building language infrastructure.

Rust was chosen as the primary code-generation target because it uniquely satisfies all five constraints:
- **Type system**: Rust's ownership and borrow checker provide compile-time guarantees that would otherwise require runtime checks.
- **Performance**: Rust compiles to native code with zero-cost abstractions. It is comparable to C++ in performance.
- **Cross-platform**: Rust runs on every major platform (Linux, Windows, macOS, iOS, Android, embedded systems).
- **WASM**: Rust compiles to WebAssembly, which runs in any browser or WASM runtime. This provides a single compiled artifact that runs everywhere.
- **Formal verification**: Rust integrates with tools like Coq and Lean. Several formal-verification projects target Rust.

WASM was chosen as the deployment target because:
- It runs in browsers without requiring a separate runtime.
- It provides a sandbox that improves security.
- It is language-agnostic: Rust code compiled to WASM can be called from JavaScript, Python, Go, etc.

---

## Decision

The Trenza compiler generates **Rust code**. The primary deployment target is **WASM** (via `wasm-pack` and the Rust WASM ecosystem).

### Compilation pipeline

```
.trz source → Trenza compiler (Rust) → Rust code + tests
           → rustc → native binary
           → wasm-pack → .wasm module (for browsers and Node.js)
```

### Secondary targets

While Rust is the primary generated language, the architecture allows future generators for:
- **TypeScript**: For developers who prefer the Node.js/frontend ecosystem (see ADR-022 if it exists).
- **Go**: For cloud-native deployments.
- **C++**: For performance-critical systems.

These are future work and do not block the current roadmap.

---

## Consequences

### Positive

- **One specification, many platforms**: A `.trz` file compiles to native binary, WASM, and (in future) JavaScript/TypeScript.
- **Verification can be precise**: Rust's type system allows the compiler to reason about properties that would be hidden in dynamically typed languages.
- **Performance is predictable**: Developers can reason about CPU and memory usage. There are no hidden garbage-collector pauses or JIT compilation delays.
- **The compiler can interface with formal tools**: Rust is the target of active formal-verification research. Future versions of Trenza can emit code verifiable by Coq or Lean.

### Negative / constraints

- **Rust's learning curve**: Developers unfamiliar with Rust's ownership model will need to learn it to understand generated code. However, well-generated Rust code can be learnable without deep Rust expertise.
- **WASM bundle size**: A WASM binary is larger than equivalent JavaScript. Optimization (via `wasm-opt`) is necessary for production. This is a known limitation, not unique to Trenza.
- **Runtime overhead**: WASM in browsers runs on a sandbox, which adds a small interpreter layer. For most applications, this overhead is negligible; for real-time systems (games, audio processing), native binaries are preferred.
- **Dependency management**: Rust's `cargo` ecosystem is powerful but can be complex. Trenza's package distribution model must interface cleanly with cargo (see ADR-022 onwards).

---

## Alternatives considered

1. **JavaScript/TypeScript as the primary target**: Rejected. Type safety is weaker; verification is harder. WASM is a better compilation target for the same use cases.

2. **Go as the primary target**: Rejected. Go's type system is less expressive than Rust's. Formal verification is not a mature tool in the Go ecosystem.

3. **Java/JVM as the primary target**: Rejected. JVM adds significant runtime overhead. Performance in constrained environments (mobile, IoT) is compromised. WASM provides better cross-platform reach.

4. **Generate multiple targets simultaneously** (Rust + Go + TypeScript): Rejected for v0.0.1. Maintaining three code generators is a maintenance burden disproportionate to immediate value. The architecture allows this later; starting with Rust is the right choice.

5. **Compile to LLVM IR directly** (bypassing Rust as an intermediate): Rejected. LLVM IR is not human-readable. Rust code is readable and can be reviewed by developers. The cost of the extra compilation step (Rust → LLVM) is negligible compared to the benefit of maintainability.

## Relation to other ADRs

- **ADR-001** (Trenza is a DSL): This ADR follows from ADR-001. The choice of Rust enables exhaustive compile-time verification.
- **ADR-003** (One file per context): WASM compilation benefits from modular contexts. Each context can be compiled as an independent module, loaded dynamically.
- **ADR-006** (`effects:` instead of `lifecycle:`): The `effects:` section maps cleanly to Rust's `Future` and async/await, making code generation straightforward.
- **Future ADRs** (TypeScript, Go targets): Will reference this ADR as the primary target, explaining why secondary targets are generated differently.
